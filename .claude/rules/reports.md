# Правила для текстов отчётов и пояснительной записки

- Исходник — Markdown в синтаксисе `tools/md2docx/README.md`; .docx только генерируется, вручную не редактируется Claude.
- Стиль — научно-технический, безличный («разработана», «выполнено»), без «мы/я», без эмодзи, без markdown-украшений вне поддерживаемого синтаксиса.
- Отчёт по лабе содержит ровно пункты «Отчёт» для этой лабы из `docs/task/labs.md`, в том же порядке, плюс короткие выводы. Шапка: тема, цель, задание.
- Каждый рисунок, таблица и листинг — с подписью и меткой `{#…}`, и на каждый есть ссылка `[@…]` в тексте **до** объекта.
- Скриншоты: файлы в `labs/labNN/screenshots/` с говорящими именами (`schema.png`, `table_contract_design.png`). Если скриншота нет — всё равно ставить ссылку на ожидаемое имя: генератор вставит заглушку, а студент увидит, что снять. Список ожидаемых скриншотов — в `labs/labNN/README.md`.
- Код в отчёте — фрагменты из реальных файлов `db/`/`client/`, не переписанные по памяти; длинные листинги — в приложение ПЗ, в отчёт — ключевые части.
- Таблицы полей (типы, ключи) генерировать из фактической схемы (`COMMENT ON`, `information_schema`), а не вручную.
- Не копировать формулировки и примеры методички (особенно примеры ЛР 4 и 7 на похожей предметной области).
- Рисунки и таблицы в ПЗ нумеруются сквозной нумерацией; в приложениях — с буквой («А.1»).

## Оформление отчётов и ПЗ — обязательные требования студента (28.10.2026)

- **Только Times New Roman** во всём документе: обычный текст, листинги, таблицы, подписи, титульный лист, ТЗ, колонтитулы, маркеры и номера списков. Никаких Courier, Consolas, Arial, Calibri, Symbol и шрифтов темы (`asciiTheme` и т. п.). Проверка — по PDF: `pdffonts` должен показать только Times New Roman (и его начертания).
- **Код в основной части ПЗ — рисунок** (уточнение студента 28.10): фрагмент кода в рамке, под ним «Рисунок N.k – …» по центру (как в образце оформления), целиком на одной странице, не разрывается. **В рамку берётся только код, подпись — вне рамки** (12:26): рамка — границы абзацев кода (`w:pBdr`), у всех абзацев кода `keepNext`, подпись — следующий обычный абзац (не строка таблицы). Не помещается — уменьшать кегль, но не меньше 7 пт; иначе — делить по смыслу на несколько рисунков. Подписей «Листинг …» в основной части нет.
- **Листинги в приложениях А, Б, В** (уточнение студента 28.10, 19:32–19:34): листинги **никак не обозначаются** — ни подписей «Листинг …», ни номеров; в приложении с листингами **нет ничего, кроме кода** (ни вступительного текста, ни таблиц состава файлов). Код — текст как есть, сплошь **в три колонки, Times New Roman 11 пт** (раздел Word с тремя колонками, фрагменты разделены пустой строкой); берутся только ключевые объекты в сокращении, пропуски — «…».
- **В 4.1–4.2 нет таблиц схемы** (решение студента 30.10, 20:02): ни таблицы связей между сущностями, ни таблиц доменов, справочников, структуры таблиц и индексов (`tools/schema2md.py` в записку не вставлять), ни рисунка схемы данных pgAdmin (ERD). Правила удаления связей, домены, индексы и последовательности описываются текстом; структура — рисунок «Создание таблицы «Договор»» и концептуальная модель.
- **Результат запроса — скриншот**: экран клиента Qt (для объектов БД — pgAdmin), без кода запроса на снимке — код уже приведён в листинге над рисунком. Таблицы с выводом psql вместо снимков не допускаются.
- **Описания запросов и объектов — короткие**: одна-две строки — что делает, кто и где использует, какая конструкция SQL. Код не пересказывать.
- **Подписи**: «Рисунок N.k – …» под рисунком (и под кодом в основной части), по центру; «Таблица N.k – …» над таблицей; у листингов приложений подписей нет. Тире в подписи — среднее «–». На каждый объект — ссылка в тексте **до** него. Нумерация сквозная внутри раздела (N — номер раздела), в приложениях — с буквой: «Рисунок А.1».
- **Стиль** — научно-технический, безличный, без «мы/я».
- Код в рисунках и приложениях — только из реальных файлов, вырезается скриптом, вручную не переписывается.
- **Не выдумывать**: раздел без основы в коде — видимая заглушка «[ЗАГЛУШКА: …]» и запись в список недоделанного (`coursework/pz/_todo.md`); нереализованное не описывать как готовое.
- **Объём** (уточнение 13:05): весь курсовой — около 100 страниц **вместе с ТЗ и приложениями** и с учётом ещё не написанного (триггеры, политики RLS, модифицируемое представление, формы ввода, тесты, снимки pgAdmin); поэтому сейчас всего не больше 90 страниц (30.10: все снимки вставлены, резерв — под ненаписанное), бюджет по разделам — `BUDGET` в `tools/pzbuild.py`, отчёт — `coursework/out/pz_report.txt`. Дописывая раздел, сокращать другие части, чтобы итог оставался около 100. Приёмы сокращения: снимки обрезать (`crop=form|main`, `trim`, `squeeze`), мелкие снимки — по два в строку, код — только существенная часть (`head=`, `lines:`), 8–9 пт; в приложениях — меньше ключевых объектов, руководства ссылаются на рисунки основной части, а не повторяют снимки.
- **Ссылки на ТЗ в тексте ПЗ крайне нежелательны** (12:26): само ТЗ вшивается после титула, но в разделах не писать «ТЗ», «п. N ТЗ», «техническое задание», «требуемых заданием» — формулировать суть требования.
- **Литература — не больше 4 источников**, ссылка всегда на один: «[2]»; «[1, 2, 4]», «[1, 3]», «[3–5]» недопустимы (12:26). Сборщик проверяет это и упоминания ТЗ (ошибки в `pz_report.txt`).
- Сборка ПЗ — `python tools/pzbuild.py` (по образцу `tools/labreport.py`, шаблон `tools/md2docx/templates/pz-template.docx`), результат — `coursework/out/pz.docx`; перед сдачей — PDF, подсчёт страниц основной части и приложений, `pdffonts`, проверка разрывов листингов, нумерации и ссылок.
