# Заключение

В курсовом проекте разработана клиент-серверная информационная система учёта услуг связи интернет-провайдеров (вариант Б-16), в которой логика программного обеспечения размещена на сервере PostgreSQL, а настольное приложение на Qt 6 выполняет функции тонкого клиента.

По задачам, поставленным во введении, получены следующие результаты.

1. Построена концептуальная модель предметной области по методике IDEF1X: восемь сущностей предметной области в третьей нормальной форме и две служебные таблицы; обоснована денормализация — хранение скидки и стоимости сеанса на момент регистрации. Абоненты образуют общий реестр объединения провайдеров, договор является таблицей пересечения провайдера и абонента.
2. Создана база данных из пяти схем с десятью доменами, внешними ключами с выбранными правилами удаления, индексами под условия экранов и явной последовательностью номеров договоров; таблицы заполнены воспроизводимыми псевдослучайными данными — более 520 000 строк. Таблица сеансов секционирована по году и вложенным кварталам, таблица договоров — по провайдерам; секции новых лет и провайдеров создаются функциями и триггером.
3. Реализованы пять групп пользователей средствами PostgreSQL, доступ только через функции и представления схемы api с проверкой группы, ограничение видимости строк провайдером пользователя, создание и блокировка учётных записей из приложения, сброс пароля с временным паролем.
4. Разработаны 23 запроса на выборку всех основных видов: запросы без параметров оформлены представлениями, запросы с параметрами — функциями; запросы 1–16, объединение и подзапрос с CASE являются источниками данных экранов, отчётов и счётчиков клиентского приложения. Тексты запросов оптимизированы, использование индексов подтверждено планами выполнения.
5. Разработано клиентское приложение: интерфейс по группе пользователя, постраничный вывод, поиск и отбор на сервере, составная форма «абонент — договоры — сеансы», отчёты с диаграммами, выгрузкой в Excel и печатью, страницы администраторов.
6. Корректность серверной части подтверждена 140 автоматическими тестами, в том числе проверками секционирования, защиты от несанкционированного доступа, оптимистической блокировки и каскадного удаления.

Часть требований к системе на момент оформления записки не реализована: триггеры (кроме проверки логина сотрудника) и модифицируемое представление, политики защиты на уровне строк, формы создания и изменения абонентов, договоров, сеансов и справочников в клиенте. Для них в записке оставлены отметки, а порядок реализации определён в документации проекта.

Предложения по развитию системы: перевести ограничение строк с условий в функциях на политики RLS с сохранением функций api как единственной точки доступа, заполнять журнал изменений триггерами, переписать отбор договоров без сеансов с условием на время, чтобы он читал только нужные секции сеансов, добавить загрузку учётных записей сеансов из биллинговых систем провайдеров в формате JSON.
