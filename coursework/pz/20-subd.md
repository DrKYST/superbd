# 2 Обоснование выбора СУБД, описание возможностей СУБД

Кроме реляционных таблиц PostgreSQL хранит слабоструктурированные данные в типе `jsonb` — двоичном представлении документа JSON с индексируемым доступом к ключам. В предметной области такие данные — учётные записи сеансов, которые биллинг провайдера выгружает по каждому сеансу: набор атрибутов в них зависит от производителя оборудования доступа (ограничение скорости, пул адресов, порт и признак должника передаются у MikroTik, Cisco, Juniper, Huawei разными ключами) и меняется со сменой оборудования, поэтому запись хранится целиком, а нужные поля извлекаются запросами. Для работы с документами СУБД предоставляет операторы извлечения значения по ключу и пути (`->`, `->>`, `#>`, `#>>`), проверки вхождения образца и наличия ключей (`@>`, `?`, `?|`), язык путей SQL/JSON (`jsonpath`: операторы `@?`, `@@`, функции `jsonb_path_query` с переменными), функции разбора документа в строки таблицы (`jsonb_to_record`, `jsonb_populate_record`) и сборки документа из строк (`jsonb_build_object`, `jsonb_agg`), изменения части документа без его перезаписи вручную (`jsonb_set`, `jsonb_insert`, `||`, `-`, `#-`). Поиск ускоряют обратные индексы GIN по документу целиком (класс операторов `jsonb_path_ops` — для поиска по образцу и `jsonpath`, `jsonb_ops` — также для проверки наличия ключей) и индексы B-дерева по выражению над отдельным ключом. На 100 025 учётных записях, построенных из данных системы, индексы сократили время типовых запросов оператора и инженера с десятков миллисекунд до долей миллисекунды; учётная запись разбирается в строку таблицы сеансов `core.session` функцией `jsonb_populate_record`. В самой системе тип `jsonb` используется для журнала изменений `audit.change_log`: строка до и после изменения хранится документом, поэтому журнал не зависит от структуры таблиц.
