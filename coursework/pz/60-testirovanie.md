## 6.1 Защита от несанкционированного доступа

Проверяется, что пользователь не может получить данные в обход функций api и сверх прав своей группы:

- оператор не читает таблицы схемы core напрямую — ошибка «нет доступа к таблице» (тест 6.2);
- пользователь без группы не получает доступа к схеме api (6.4), функции api и sec не выполняются от имени PUBLIC (6.5), внутреннюю функцию sec.provider_scope оператор вызвать не может (7.18);
- администратору БД закрыты экраны данных абонентов и провайдеров (10.2), администратору приложения — журнал изменений и состояние базы (10.7); администратор приложения не создаёт администраторов (10.10);
- оператор другого провайдера не видит сеансы и договоры чужого провайдера (7.5, 9.8), договор с чужим абонентом по коду не заключить — перебор кодов ничего не даёт (9.5);
- с временным паролем доступны только сведения о себе и смена пароля, остальные функции отказывают с кодом SB001 (11.3); временный пароль не сохраняется ни в одной таблице проекта (11.5);
- ввод служебных символов шаблона «%» и «_» в поиск не выбирает все строки (7.14); значения передаются параметрами, поэтому ввод вида «' OR 1=1 --» обрабатывается как обычная строка поиска.

## 6.2 Одновременная работа с данными

Изменение абонента и договора выполняется с оптимистической блокировкой: клиент передаёт прочитанную версию строки, функция изменяет строку только при совпадении версии и увеличивает её. Тест 9.11 моделирует двух пользователей: первое изменение проходит (версия 1 → 2), повторное изменение с устаревшей версией отклоняется с кодом 40001 и сообщением «Абонент изменён другим пользователем — обновите карточку». Одновременное создание абонента с тем же наименованием и телефоном не создаёт дубль благодаря уникальному индексу (тесты 5.5, 9.6, 9.10).

## 6.3 Каскадное удаление

Удаление абонента каскадно удаляет его договоры и сеансы (тест 5.1: договоров 6 → 0, сеансов 68 → 0). Удаление тарифа, на который ссылаются сеансы, и провайдера с договорами отклоняется ограничением RESTRICT (5.3, 5.4). Удалить общего абонента, обслуживаемого несколькими провайдерами, нельзя никому: каскадом были бы удалены чужие договоры (9.16).

## 6.4 Корректность запросов и отчётов

Результат каждого запроса сравнивается с независимым расчётом другим способом: например, список договоров без сеансов — с расчётом через NOT EXISTS (12.5), выручка за месяц — с прямой суммой операций (12.7), строка «Итого» — с суммой периодов (12.8); число строк объединения — с числом договоров и сеансов (12.9). Проверены также совпадение счётчиков начальной страницы со списками (12.6, 12.10), совпадение результата запроса 19 с индексным доступом и без него (14.8) и независимость результата от часового пояса клиента (6.7). Секционирование проверяется на рабочей базе: каждая строка лежит в секции своего квартала или провайдера, а секции по умолчанию пусты (13.3), запрос за квартал читает одну секцию сеансов, запрос провайдера — одну секцию договоров (13.4), при общем плане с параметрами лишние секции исключаются при выполнении (13.5), регистрация провайдера создаёт его секцию договоров (13.6).
