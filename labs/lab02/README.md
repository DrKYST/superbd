## Вопросы к защите

**Предметная область** — часть реального мира, данные о которой хранятся и обрабатываются в системе. Здесь — учёт услуг интернет-провайдеров: провайдеры, абоненты, договоры, сеансы связи.

**База данных** — совокупность взаимосвязанных данных, организованных по определённым правилам и хранящихся под управлением СУБД. **СУБД** — программный комплекс для создания БД, хранения, изменения и извлечения данных, контроля целостности и разграничения доступа (здесь PostgreSQL).

**Реляционная модель данных** (Э. Кодд, 1970) — данные представлены набором отношений (таблиц); отношение — множество кортежей (строк) с одинаковым набором атрибутов (столбцов); каждый атрибут принимает значения из своего домена. Операции — реляционная алгебра (выборка, проекция, соединение и др.).

**Домен** — множество допустимых значений атрибута. В модели — `d_name`, `d_phone`, `d_money`, `d_price_mb`, `d_percent`, `d_mb`, `d_year`, `d_address`, `d_contract_no` (в PostgreSQL — `CREATE DOMAIN` с CHECK).

**Нормализованная таблица** — таблица без избыточности, приводящей к аномалиям. **Нормализация** — пошаговая декомпозиция отношений для устранения избыточности и аномалий обновления, включения и удаления.

**1НФ** — все значения атомарны, нет повторяющихся групп. Пример: сеансы договора разворачиваются в отдельные строки; адрес разделён на город и адрес.

**2НФ** — 1НФ и каждый неключевой атрибут полностью зависит от всего первичного ключа (нет зависимостей от части составного ключа). Пример: реквизиты провайдера зависели только от «Провайдера» — часть ключа {Провайдер, Номер договора, Дата сеанса} — и вынесены в отдельную таблицу.

**3НФ** — 2НФ и нет транзитивных зависимостей неключевых атрибутов от ключа. Пример: договор → абонент → тип абонента; сеанс → тариф → скидка. Абонент и тариф вынесены в отдельные таблицы.

**Аномалии**: обновления — одно и то же значение хранится в нескольких строках, изменение не во всех строках даёт противоречие; включения — нельзя добавить данные об объекте без данных о другом (провайдера без сеанса); удаления — удаление строки уничтожает посторонние сведения (последний сеанс — и сведения о договоре).

**Первичный ключ** — атрибут или набор атрибутов, однозначно идентифицирующий строку; не NULL, уникален. **Естественный** ключ — из предметной области (название провайдера, номер договора в паре с провайдером). **Составной** — из нескольких атрибутов ({`id`, `started_at`} в сеансе, {`provider_id`, `contract_no`}). **Искусственный (суррогатный)** — вводится только для идентификации: числовой счётчик (`GENERATED ALWAYS AS IDENTITY`), символьный код. В модели все PK — суррогатные: естественные ключи длинные, меняются или уникальны только в паре.

**Почему у сеанса составной PK** — таблица будет секционирована по `started_at` (ЛР 8), а PostgreSQL требует, чтобы первичный ключ секционированной таблицы включал ключ секционирования.

**Альтернативный ключ** — другой уникальный набор атрибутов, не выбранный первичным (название провайдера, {провайдер, номер договора}). **Частичный уникальный ключ** — уникальность только для части строк: IP уникален среди действующих договоров провайдера (`WHERE closed_on IS NULL`).

**Внешний ключ** — атрибут потомка, значения которого совпадают со значениями первичного ключа родителя (`contract.provider_id` → `provider.id`).

**Целостность данных** — соответствие данных правилам предметной области: ограничения доменов, NOT NULL, уникальность, CHECK, триггеры. **Ссылочная целостность** — каждое значение внешнего ключа ссылается на существующую строку родителя; обеспечивается FK и правилами ON DELETE: RESTRICT (запрет удаления — справочники, провайдер), CASCADE (каскадное удаление — абонент → договоры → сеансы), SET NULL.

**Виды связей**: 1:1 (одной записи соответствует не более одной), 1:N (провайдер — договоры, абонент — договоры, договор — сеансы), M:N (провайдер — абонент, пользователь — группа). M:N в реляционной модели реализуется через таблицу пересечения: провайдер и абонент связаны через «Договор» (один абонент — клиент нескольких провайдеров, D25), пользователи и группы — через системную «Членство в группе» (`pg_auth_members`). В договоре хранится то, что относится к паре «провайдер — абонент»: номер, цены, IP, адрес подключения, контакты. Связь идентифицирующая, если FK входит в PK потомка; у нас все связи неидентифицирующие (суррогатные ключи). Обязательная — у потомка FK NOT NULL.

**Базовые таблицы и справочники** — справочники хранят ограниченные наборы значений, меняются редко (тип собственности, город, тип абонента, тариф); базовые — основные объекты учёта, растут в процессе работы (провайдер, абонент, договор, сеанс).

**Зачем денормализация в сеансе** — стоимость уже оказанной услуги не должна меняться при изменении тарифа или цены договора, а отчёты по сотням тысяч сеансов не пересчитывают формулу (`model.md`, п. 2.5).

**Почему IP в договоре** — IP выдаёт провайдер по договору; у абонента может быть несколько договоров (точек подключения), у каждого свой IP → у абонента атрибут был бы многозначным (нарушение 1НФ).

**Почему `numeric`, а не `float` / `money`** — `float` двоичный, даёт ошибки округления в деньгах; `money` зависит от локали сервера и имеет фиксированные 2 знака, а цене 1 Мб нужно 4.
