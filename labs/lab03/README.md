## Как пересобрать

```bash
psql -U postgres -d postgres -v ON_ERROR_STOP=1 -f db/create_db.sql
```
```bash
psql -U postgres -d superbd -v ON_ERROR_STOP=1 -f db/build.sql
```
```bash
psql -U postgres -d superbd -v ON_ERROR_STOP=1 -f db/tests/run_all.sql
```

Первая команда нужна один раз. Сборка занимает около 5 секунд. Роли кластерные: `build.sql` пересоздаёт схемы, но существующие роли не удаляет.

После изменения схемы обновить таблицы в ПЗ: `python tools/schema2md.py --update coursework/pz/40-bd.md`.

## Вопросы к защите

**Порядок создания таблиц.** Сначала таблицы стороны «один» (справочники, провайдер, абонент), затем подчинённые (договор, сеанс): внешний ключ может ссылаться только на уже существующую таблицу. Заполнение — в том же порядке: строку потомка нельзя вставить, пока нет строки родителя.

**Что такое подстановка и как она сделана в PostgreSQL.** В Access подстановка — свойство поля: вместо кода показывается значение из связанной таблицы (выпадающий список). В PostgreSQL такого свойства у колонки нет: в таблице хранится код (`provider_id`) с внешним ключом, а подстановку делает клиент — выпадающий список заполняется функцией `api.*_lookup()` (название на экране, код скрыт в `Qt::UserRole`).

**Схема данных** — таблицы и связи между ними; в PostgreSQL связи задаются внешними ключами (`FOREIGN KEY … REFERENCES`), а pgAdmin строит по ним диаграмму (ERD Tool). Тип связи — «один ко многим»: у родителя «ровно один» (черта), у потомка «ноль или много» («воронья лапка» с кружком).

**Свойства полей в PostgreSQL:** тип или домен, NOT NULL (обязательность), DEFAULT (значение по умолчанию), CHECK (условие на значение), PRIMARY KEY, UNIQUE, FOREIGN KEY, `GENERATED ALWAYS AS IDENTITY` (счётчик), комментарий (`COMMENT ON COLUMN` — «подпись» поля).

**Зачем домены.** Одно ограничение (формат телефона, неотрицательная сумма) описывается один раз и используется во многих колонках; при изменении правила меняется только домен.

**RESTRICT, CASCADE, NO ACTION.** RESTRICT — удаление родителя запрещено сразу, если есть ссылки (справочники, провайдер); CASCADE — вместе с родителем удаляются потомки (абонент → договоры → сеансы); NO ACTION — как RESTRICT, но проверка может быть отложена до конца транзакции.

**Почему у сеанса составной первичный ключ.** Таблица будет секционирована по дате сеанса (ЛР 8), а первичный ключ секционированной таблицы обязан включать ключ секционирования.

**Почему абонент в общем реестре (D25).** Одно лицо или предприятие у двух провайдеров — одна запись: нет дублей и расхождений в наименовании и телефоне. Договор — таблица пересечения провайдера и абонента; в нём хранится то, что у разных провайдеров разное: номер, цены, IP, адрес подключения, контактный телефон и лицо. Провайдер видит абонента, пока у него есть договор с ним. Сведения общего абонента меняет только администратор, удалить такого абонента нельзя (каскадом ушли бы чужие договоры). Раньше (D17) у каждого провайдера были свои копии абонента — от этого отказались: копии расходились.

**Частичный уникальный индекс.** `UNIQUE (provider_id, ip_address) WHERE closed_on IS NULL` — IP уникален только среди действующих договоров провайдера; после расторжения адрес можно выдать снова.

**Индексы.** PostgreSQL сам создаёт индексы только для PRIMARY KEY и UNIQUE; для внешних ключей их создают вручную — иначе соединения и удаление родителя требуют полного просмотра таблицы потомка. Индекс по `lower(name) text_pattern_ops` ускоряет поиск `lower(name) LIKE 'ива%'`.

**Последовательность.** Объект, выдающий возрастающие числа (`nextval`). Колонки identity используют неявные последовательности; `core.contract_no_seq` создана явно для номеров договоров «Д-2025-000123».

**Где пользователи и почему нет таблицы users.** Пользователи — LOGIN-роли PostgreSQL (`pg_authid`), группы — роли без входа, членство — `pg_auth_members`. Пароли хранит СУБД (хеш SCRAM-SHA-256). `sec.app_user` хранит только ФИО и провайдера сотрудника; соответствие логина роли проверяет триггер, потому что внешний ключ на системный каталог поставить нельзя.

**Как получены 120 000 строк.** SQL-генератор: `generate_series` задаёт количество, `random()` выбирает значения из массивов фамилий, имён, улиц; `setseed(0.16)` делает результат повторяемым; стоимость сеанса вычисляется по формуле прямо в INSERT.

## Следующий шаг

Этап курсовой вне лабораторных — «роли + RLS + функции api»: `sec.current_group()`, `sec.current_provider_id()`, политики RLS на `core.*`, функции `api.*` (CRUD, списки с пагинацией), GRANT группам, тесты `SET SESSION AUTHORIZATION`. После него демо-пользователи смогут работать с данными.
