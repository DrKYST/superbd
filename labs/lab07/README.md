## Главное

Документ — **учётная запись сеанса связи из биллинга провайдера** (D29): то, что в `docs/analysis/domain.md` названо «в реальности — загрузка из биллинга». Её присылает сервер доступа (NAS) провайдера; у разных производителей (MikroTik, Cisco, Juniper, Huawei, Accel-PPP) набор атрибутов разный, поэтому запись хранится целиком в `jsonb`, а в строку `core.session` курсовой разбирается запросом (5.4; сверка 5.5 — 100 025 из 100 025 записей совпали с сеансами курсовой).

Данные порождены из базы курсовой: каждый сеанс `core.session` → учётная запись (договор, провайдер, тариф, объём, скидка, стоимость — из `core`/`ref`; узел доступа, длительность, причина завершения, трафик по направлениям, атрибуты производителя, журнал событий — достроены). Плюс `generate_series`: 400 служебных сеансов наладки NAS и 1 200 неудачных подключений — их удаляет шаг 7. Результат повторяем (`setseed`, один поток): два прогона генерации дают одинаковый md5 всех документов.

Схема `lab7` — песочница лабораторной: основную базу (`core`, `ref`, `api`) скрипты не меняют, `db/migrations` не тронуты. Проверено 12.10 на пробной базе, собранной с нуля: тесты курсовой — 117 из 117, затем все шаги ЛР 7 (29 с), сверка 5.5 — 100 025 из 100 025; повторная `build.sql` поверх схемы `lab7` проходит.

## Индексы и оптимизация

| Индекс | Вид | Под какие запросы |
|---|---|---|
| `ix_session_record_doc` | GIN `(doc jsonb_path_ops)` — документ целиком | `@>` (договор, город узла, причина), `@?`/`@@` (события журнала, производитель + тариф): 3.1, 3.3, 4.1–4.3, 5.1, 5.4, 5.6, 9.1, 9.2, 9.6 |
| `ix_session_record_attributes` | GIN `((doc -> 'attributes'))`, `jsonb_ops` | наличие атрибута `?`, `?|`: 3.2, 9.3 |
| `uq_session_record_provider_acct` | уникальный B-дерево `((doc #>> '{source,provider,name}'), (doc #>> '{session,acct_id}'))` | запрет повторной загрузки сеанса; поиск по Acct-Session-Id: 5.3, 9.4 |
| `ix_session_record_started_at` | B-дерево `((doc #>> '{session,started_at}') COLLATE "C")` | отбор за период: 9.5 |

Почему `jsonb_path_ops` для документа целиком: запросы к документу — поиск по образцу и по jsonpath с равенствами; `jsonb_path_ops` их поддерживает, а элемент индекса — хеш пути вместе со значением («`source.nas.vendor` = Huawei»), поэтому образец из нескольких ключей отбирает точнее, чем `jsonb_ops` (там «vendor» и «Huawei» — отдельные элементы), и индекс меньше: 75 МБ против 85 МБ (`explain/08_indexes.txt`). Проверка наличия ключа (`?`) нужна только для атрибутов — для них отдельный маленький индекс `jsonb_ops` (8 МБ).

Оптимизации (точные числа последнего прогона — `explain/INDEX.md`; время меняется от прогона к прогону на 10–30 %):

| № | Что изменено | Индекс | cost до → после | Время |
|---|---|---|---|---|
| 9.1 | `doc -> … ->> 'number' = …` → `doc @> '{…}'` | GIN по документу | ≈ 22 070 → 3 356 | десятки мс → 0,1 мс |
| 9.2 | `jsonb_path_exists(doc, …, vars)` → `doc @? '…'` | GIN по документу | ≈ 22 560 → 3 354 | ≈ 70 мс → ≈ 5 мс |
| 9.3 | запрос тот же, добавлен индекс по атрибутам (`BitmapAnd` двух GIN) | GIN по атрибутам + по документу | ≈ 21 970 → 60–190 | ≈ 70 мс → < 1 мс |
| 9.4 | `doc -> 'session' ->> 'acct_id'` → `doc #>> '{session,acct_id}'` (как в индексе) | уникальный B-дерево | ≈ 22 070 → 8,45 | ≈ 60 мс → 0,05 мс |
| 9.5 | `(…)::timestamptz >= …` → `(…) COLLATE "C" >= …` | B-дерево по времени | ≈ 22 280 → 18 490 | ≈ 120 мс → ≈ 20 мс |
| 9.6 | `#>> = 'Huawei' AND #>> = 'ВН'` → `doc @@ '… && …'` | GIN по документу | ≈ 22 170 → 3 354 | ≈ 60–130 мс → ≈ 8–10 мс |

Где индекс не помог — показано честно:

- **9.7** — сравнение «больше» внутри jsonpath (`@.mb > 400`): GIN хранит пары «путь = значение» и диапазон не ищет, план не меняется (Seq Scan). Если такой отбор нужен часто — B-дерево по выражению `((doc #>> '{session,traffic,out,mb}')::numeric)`.
- **9.8** — условие, которому отвечает больше половины записей (`stop_cause = user_request`, 55 %): для `@>` по `jsonb` статистики по содержимому нет, планировщик оценивает 1 000 строк вместо ~55 000 и выбирает индекс, но читает почти все страницы таблицы — время то же, что у Seq Scan (план с `enable_bitmapscan = off` в том же файле). Оценка cost «после» (3 367) занижена — пример того, что по cost без actual time выводы делать нельзя.
- **4.4, 5.2, 5.5** — индекс не используется по существу запроса: условие-диапазон и отрицание (4.4), нужны все записи (5.2, 5.5).
- **9.5** — выигрыш по времени в 6–7 раз, а по cost всего 17 %: за сентябрь 2026 года — 11 % всех записей (данные растут со временем), и планировщик считает чтение 2 250 страниц из 20 000 по битовой карте почти таким же дорогим, как последовательное.

Почему индекс по времени — строка, а не `timestamptz`: приведение `text → timestamptz` зависит от настроек сеанса (функция `STABLE`), в выражении индекса допустимы только `IMMUTABLE`. Время в документах — ISO 8601 с одним смещением `+03:00`, поэтому побайтовое сравнение строк (`COLLATE "C"`) совпадает со сравнением моментов времени; результаты 9.5 «до» и «после» совпадают.

## Вопросы к защите

**Чем `->` отличается от `->>` (и `#>` от `#>>`).** `->` возвращает значение по ключу (или по номеру элемента массива) как `jsonb` — с ним можно продолжать путь (`doc -> 'source' -> 'nas'`); `->>` — как `text`, конец пути, годится для сравнения со строкой и приведения типов. `#>` / `#>>` — то же по пути из нескольких ключей (`doc #>> '{session,started_at}'`). Числа из `->>` приходят строкой: `(doc #>> '{billing,cost}')::numeric`.

**`json` и `jsonb`.** `json` хранит текст как есть (пробелы, порядок ключей, повторяющиеся ключи) и разбирает его при каждом обращении. `jsonb` хранит разобранное двоичное представление: ключи объекта отсортированы и без дублей (остаётся последний), пробелы не сохраняются; ввод чуть медленнее, зато доступ к ключам быстрый, есть операторы `@>`, `?`, jsonpath-операторы `@?`/`@@` и GIN-индексы. Для учётных записей, которые пишутся один раз и много раз ищутся, — `jsonb`.

**`jsonb_ops` и `jsonb_path_ops`.** Оба — классы операторов GIN. `jsonb_ops` (по умолчанию) кладёт в индекс отдельно каждый ключ и каждое значение и поддерживает `@>`, `?`, `?|`, `?&`, `@?`, `@@`. `jsonb_path_ops` кладёт хеш пути вместе со значением, поддерживает только `@>`, `@?`, `@@`, но индекс меньше, а поиск по образцу из нескольких ключей точнее (меньше лишних строк на перепроверку). Здесь: документ целиком — `jsonb_path_ops` (75 МБ против 85 МБ), атрибуты — `jsonb_ops` ради `?|`.

**Когда GIN по `jsonb` не используется.** (1) Условие записано не оператором, а функцией или сравнением извлечённого значения: `doc ->> 'x' = …`, `jsonb_path_exists(…)` — индекс по документу их не обслуживает (9.1, 9.2), нужен оператор `@>`/`@?`/`@@` или B-дерево по выражению. (2) Диапазоны (`>`, `<`) внутри jsonpath — GIN хранит только «есть / равно» (9.7). (3) Отрицание (`NOT @>`, 4.4). (4) Условию отвечает большая часть таблицы — чтение целиком не хуже (9.8). (5) Выражение B-дерева должно совпадать с выражением в запросе буквально: индекс по `doc #>> '{session,acct_id}'` не применяется к `doc -> 'session' ->> 'acct_id'` (9.4).

**Оценка строк для `jsonb`.** Для `@>`, `@?`, `@@` статистики по содержимому документа нет — планировщик берёт постоянную долю (здесь 1 000 строк из 100 025 при любом образце). У B-дерева по выражению `ANALYZE` собирает статистику выражения — в 9.5 оценка 11 003 строки при фактических 11 134. Поэтому часто используемые ключи стоит индексировать B-деревом по выражению или выносить в обычные колонки (как в `core.session`).

**TOAST для больших документов.** Строка таблицы должна помещаться в страницу 8 КБ; значение длиннее ~2 КБ PostgreSQL сначала сжимает (`pglz` или `lz4`), а если не помогло — выносит в отдельную TOAST-таблицу, оставляя в строке ссылку. Чтение любого ключа такого документа требует извлечь и распаковать его целиком. Здесь записи 1,4–1,8 КБ (`explain/02_generate.txt`) — хранятся в строке без сжатия; при больших документах полезно держать часто читаемые поля отдельными колонками, а журнал событий — не раздувать.

**Зачем `jsonb_set` с `create_missing` и `jsonb_set_lax`.** `jsonb_set(doc, путь, значение, true)` создаёт последний ключ пути, если его нет (6.2: номер счёта), но не промежуточные объекты. `jsonb_set` с `NULL` в качестве значения возвращает `NULL` — весь документ пропал бы; `jsonb_set_lax` определяет, что делать с `NULL`: записать JSON `null`, удалить ключ (`'delete_key'`, 6.3), вернуть документ без изменений или ошибку.

**`jsonb_insert`: до или после.** Путь указывает элемент массива (`-1` — последний); `insert_after = false` вставляет перед ним (6.4: событие CoA перед `stop`), `true` — после (6.5: обновление после `start`). Для ключа объекта `jsonb_insert` ключ не заменяет, а выдаёт ошибку, если он уже есть.

**Почему удаление отбором `@>` и `@?`, а не по `->>`.** Те же условия обслуживает индекс по документу; служебная запись `{"contract": null}` отбирается образцом с JSON `null`.

**Где связь с курсовой.** Документ описывает реальный вход системы — выгрузку биллинга; запрос 5.4 — разбор записи в строку `core.session` (`jsonb_populate_record` в тип строки таблицы курсовой), 5.5 — сверка выгрузки с учётом. Журнал изменений курсовой `audit.change_log` (D10) тоже хранит строки в `jsonb` — его заполняют триггеры курсовой, отдельная работа.
