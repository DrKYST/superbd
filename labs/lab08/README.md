## Особенность PostgreSQL 18.3, найденная при реализации

Если присоединить (`ATTACH PARTITION`) таблицу года вместе с уже созданными квартальными секциями, identity-свойство `id` получает только таблица года, а кварталы — нет; после этого `DETACH` года падает с ошибкой «столбец id … не является столбцом идентификации». Поэтому `sec.session_partitions_ensure` присоединяет пустую таблицу года и создаёт кварталы уже внутри неё (`CREATE TABLE … PARTITION OF год`) — они наследуют identity, `DETACH` работает (`explain/04_maintenance.txt`, 4.3). В PostgreSQL 16 identity секциям не передаётся вовсе — вставка идёт только через `core.session`, так и сделано.

## Материал для подраздела 4.6 ПЗ

Таблица сеансов связи — единственная неограниченно растущая таблица системы со сроком хранения; она секционирована по дате начала сеанса в два уровня: секции годов (2024–2027) разделены на квартальные секции, сеансы года без созданной секции попадают в секцию по умолчанию. Год — единица архивирования: устаревший год отсоединяется (DETACH PARTITION) и удаляется без удаления строк; квартал — единица обслуживания и отсечения: отчёты и журналы за период читают только свои кварталы. Секции следующего года создаёт функция sec.session_partitions_ensure (при сборке базы и администратором базы данных раз в год функцией api.db_session_partitions_ensure): таблица года присоединяется к таблице сеансов, кварталы создаются внутри неё, сеансы года из секции по умолчанию переносятся в свои кварталы. Таблица договоров секционирована по списку провайдеров: у каждого провайдера своя секция, её создаёт триггер при регистрации провайдера; сотрудники провайдера работают со своей секцией (условие на провайдера в функциях схемы api отсекает остальные), аналитические отчёты — с таблицей целиком. Первичный ключ договора включает код провайдера, поэтому сеанс ссылается на договор составным внешним ключом и хранит код провайдера договора. Индексы созданы на секционированных таблицах и действуют в каждой секции. Сравнение с обычными таблицами на запросах системы показало отсечение секций при планировании и при выполнении; запросы без условия на дату сеанса (последний сеанс договора, все сеансы договора) читают все секции и выполняются медленнее.

## Вопросы к защите

**Зачем ключ секционирования в первичном ключе.** Уникальность в секционированной таблице проверяется индексом каждой секции отдельно; строки с одинаковым `id` в разных секциях индекс секции не увидит. Если в ключ входит ключ секционирования, одинаковые ключи всегда в одной секции. Поэтому PK сеанса — `(id, started_at)`, договора — `(id, provider_id)`.

**Почему абонентов нельзя разделить по провайдерам.** Абонент общий для провайдеров (D25), у 590 абонентов договоры с несколькими провайдерами; уникальность «наименование + телефон» по всему реестру на секционированной таблице не задать (уникальный индекс обязан включать провайдера) — реестр перестал бы гарантировать одну запись на абонента.

**Отсечение при планировании и при выполнении.** Если граница — константа, планировщик сразу оставляет нужные секции (3.1). Если параметр (функция PL/pgSQL, подготовленный запрос с общим планом) или `current_date`, лишние секции отбрасываются при запуске — в плане «Subplans Removed» (3.9, 3.10, тест 13.5).

**Вложенные секции.** Секция года сама секционирована по кварталам: условие на дату отсекает сначала годы, потом кварталы; отсоединить можно и год целиком, и отдельный квартал.

**Секция по умолчанию.** Получает строки, для которых нет секции (сеанс года, который ещё не создан). Пока в ней есть строки нового года, секцию этого года не присоединить — поэтому функция сначала переносит такие строки (тест 13.7).

**ATTACH и CREATE TABLE … PARTITION OF.** Присоединение готовой таблицы берёт на родителе блокировку SHARE UPDATE EXCLUSIVE — чтение и запись сеансов продолжаются; создание секции командой `PARTITION OF` — ACCESS EXCLUSIVE. Перед присоединением заполненной таблицы её стоит снабдить `CHECK` с диапазоном — тогда проверочного чтения нет (4.4).

**DETACH и DELETE.** Отсоединение — изменение каталога, данные не читаются; удаление строк читает и помечает каждую, оставляет мёртвые версии до очистки. `DETACH … CONCURRENTLY` (с PostgreSQL 14) отсоединяет без долгой блокировки, но не допускается, пока у таблицы есть секция по умолчанию (проверено: «секции нельзя отсоединять в режиме CONCURRENTLY, когда существует секция по умолчанию») — у `core.session` она есть, поэтому архивный год отсоединяется обычным `DETACH` (короткая блокировка ACCESS EXCLUSIVE, раз в год).

**Когда секции мешают.** Запрос без условия на ключ секционирования читает все секции: «все сеансы договора» — 17 спусков по индексу вместо одного (3.5); «последний сеанс» — все секции (3.8). Помогает условие на время (3.9) или ключ секционирования в условии.

**Почему не по тарифу (прежний план).** Тариф не отбирается экранами (кроме необязательного отбора журнала), отчёт по тарифам нужен целиком, обслуживать «ночные сеансы» отдельно незачем — отсечения и выгоды нет.

**Статистика секционированной таблицы.** Автоочистка анализирует секции, но не саму секционированную таблицу: её статистику обновляет только `ANALYZE core.session` — поэтому экран «Таблицы базы данных» показывает сбор статистики самой таблицы, а счётчик администратора БД её учитывает.
