# Требования методички к курсовому проекту

Источник: «Методические рекомендации по выполнению курсового проекта по дисциплине „Программирование систем с серверами баз данных“», ДонНТУ, 2024 (Чернышова А. В., Щедрин С. В., Бердюкова С. С., Филипишин Д. А.).
PDF лежит в `docs/source/`, но его текстовый слой повреждён (кириллица в нестандартной кодировке). Этот файл — проверенная расшифровка, пользоваться нужно им.

## 1. Техническое задание (приложение А методички), пункты «Задание на курсовой проект»

1. Спроектировать концептуальную модель БД для предметной области и представить её взаимосвязанными таблицами в **3НФ** (денормализацию — обосновать). Выделить базовые таблицы и таблицы-справочники, указать первичные и внешние ключи.
2. Создать БД средствами SQL. Добавить таблицы, **домены**, **индексы**.
3. Разработать **не менее шести триггеров** (по одному на каждый тип события), как минимум для **двух различных таблиц**.
   Трактовка: 6 типов = BEFORE/AFTER × INSERT/UPDATE/DELETE.
4. Заполнить таблицы SQL-запросами: **не менее 10 записей в каждом справочнике**, **10 000 – 50 000 псевдослучайных записей** в таблицах.
5. Сформулировать запросы:
   - симметричное внутреннее соединение с условием — 2 запроса с отбором по внешнему ключу, 2 — по датам;
   - симметричное внутреннее соединение без условия — 3 запроса;
   - левое внешнее соединение;
   - правое внешнее соединение;
   - запрос на запросе по принципу левого соединения;
   - итоговый запрос без условия;
   - итоговый запрос без условия с итоговыми данными вида «всего», «в том числе»;
   - итоговые запросы с условием на данные: по значению, по маске, с использованием индекса, без использования индекса;
   - итоговый запрос с условием на группы;
   - итоговый запрос с условием на данные и на группы;
   - запрос на запросе по принципу итогового запроса;
   - запрос с объединением (UNION);
   - запросы с подзапросами: с `IN`, `NOT IN`, `CASE`, операциями над итоговыми данными.
6. Запросы **без параметров** — в виде **представлений**, остальные — **хранимые процедуры и/или функции**. Минимум **одно модифицируемое представление** через триггеры (INSTEAD OF). **ВСЯ логика ПО — на сервере.**
7. Клиентское приложение должно обеспечивать:
   - многопользовательский режим (одна программа для всех ролей, ситуативный доступ к интерфейсу);
   - несколько ролей (администратор — добавление/удаление/редактирование пользователей, их прав/ролей; пользователи-1; пользователи-2 …);
   - просмотр таблиц и представлений (с учётом прав);
   - добавление, редактирование и удаление записей таблиц и модифицируемых представлений;
   - работу с наборами данных «один-ко-многим» (составная форма родитель + потомок);
   - поиск и фильтрацию;
   - просмотр результатов запросов;
   - визуализацию результатов одного из итоговых запросов (диаграммы, экспорт в Excel).
8. Защита от несанкционированного доступа, **защита на уровне строк (RLS)**, **партицирование одной из основных таблиц**.

## 2. Требования к ролям и интерфейсу (раздел 2 методички)

- Минимум **3 группы ролей** пользователей с разным набором возможностей клиента. Роль **«гость»** — если предметная область подразумевает доступ без авторизации.
- **Все роли реализуются средствами PostgreSQL**, дополнительно проверяются на бэкенде (в БД) и учитываются клиентом **только после успешной авторизации в самой СУБД**.
- **Категорически запрещено**: авторизация «как в CMS/хостингах» — пароль вшит в код, роли определяются по дополнительным таблицам приложения.
- Пример групп: «администраторы», «сотрудники», «начальники».
- Интерфейс: одна «страница» по теме, инструменты которой показываются в зависимости от роли. **Запрещено** делать отдельные страницы одинаковой тематики для каждой роли (исключение — тематика целиком принадлежит одной роли, например «редактирование пользователей» у администратора).
- **Администратор**: управление пользователями и справочниками + прочие инструменты предметной области. Ненужные ему инструменты других ролей — скрыть или заблокировать.
- **Сотрудник**: только инструменты оперативной работы (услуги, продажи, регистрация заявок и т. п.). Если сотрудники делятся по направлениям/отделам — обязательно группировать; каждый видит данные **только своего отдела/филиала**.
- **Начальник**: статистика со всевозможными фильтрами, **выгрузка в Excel**, **обязательное распределение по временным отрезкам**. Разделять начальников по направлениям/отделам, ограничивая видимость; при таком делении предусмотреть **«председателя» / «главного начальника»** со сводной информацией по всем отделам.
- **Все запросы к таблицам обёрнуты в функции** с выделением необходимых привилегий группам ролей (или персонально).
- **Пагинация** (страницы/блоки по 20/100/200 записей), размер блока выбрать самостоятельно.
- **Идентификаторы (ID) выводить на экран только если они нужны текущей роли**, иначе категорически запрещено. ID прятать в невидимые структуры/переменные клиента.

## 5. Этапы (раздел 1 методички), кратко

Выбор темы → подбор и изучение литературы (записывать точные библиографические описания) → подготовка данных → системный анализ и моделирование (главы 2–3 ПЗ, кроме описания ПО) → алгоритмизация и программирование (описание ПО, интерфейса, контрольного примера — в главу 3 и приложения) → выводы → оформление → самопроверка → регистрация на кафедре (после регистрации правки запрещены; проверка до 7 дней) → защита.
