# План запросов (ЛР 5, ЛР 6, ТЗ п. 5–6, разделы 4.7–4.8 ПЗ)

Правило ТЗ п. 6: запрос без параметров → представление `api.v_*`; с параметрами → функция `api.q_*`.
ЛР 5/6 требуют параметров почти везде, поэтому большинство — функции; представления — для запросов «без условия».
Все запросы используют данные нескольких таблиц. Названия — рабочие, уточняются при выполнении лаб.

### 11. Пользователи по группам, «всего» и «в том числе» — итоговый без условия

- **Потребность.** Панель «Группа / Кол-во» экрана «Пользователи» (макет `Users.dc.html`): жирная строка «Все пользователи — 57», под ней с отступом число пользователей каждой группы. Панель же служит отбором списка.
- **Кто.** Администратор приложения (свои и управляемые группы), администратор БД (администраторы приложения и БД), D26.
- **Объект.** `api.v_user_groups` — представление: параметров нет (ТЗ п. 6).
- **Таблицы.** `sec.app_user` ⋈ `pg_roles` (пользователь) ⋈ `pg_auth_members` ⋈ `pg_roles` (группа).
- **Почему этот тип.** Нужны количества по группам — без группировки их не получить: обычный запрос вернёт пользователей, а не числа. Условий от пользователя нет, только область видимости роли (как у представлений ЛР 5). Строка «Все пользователи» — `GROUP BY ROLLUP (группа)`: одна дополнительная группировка вместо второго запроса через `UNION ALL` или подсчёта в клиенте (логика — на сервере).
- **Группа** — то же определение, что у `sec.group_of` и списка `api.q_users` (прямое членство с наследованием, D26); каждый пользователь ровно в одной группе (тест 4.2), поэтому сумма по группам = «Все пользователи» = `total_count` списка `api.q_users()` без отбора — тест.
- **Пустые группы** в панель не попадают (группировка идёт по существующим пользователям): отбирать по группе без пользователей нечего. Если понадобится показывать и их — левое соединение со списком групп, это уже другой тип.

```sql
SELECT CASE WHEN grouping(g.rolname) = 1 THEN 'Все пользователи'
            ELSE sec.group_title(g.rolname) END AS title,
       g.rolname AS group_name,                                   -- NULL у строки «Все пользователи»
       count(*) AS users
FROM sec.app_user u
JOIN pg_catalog.pg_roles r        ON r.rolname = u.login
JOIN pg_catalog.pg_auth_members m ON m.member = r.oid AND m.inherit_option
JOIN pg_catalog.pg_roles g        ON g.oid = m.roleid
WHERE g.rolname = ANY (sec.visible_groups(sec.current_group()))
GROUP BY ROLLUP (g.rolname)
ORDER BY grouping(g.rolname) DESC,                                -- «Все пользователи» первой, как в макете
         array_position(ARRAY['grp_dba', 'grp_admin', 'grp_chief', 'grp_manager', 'grp_operator']::name[], g.rolname);
```

Проверено на копии (администратор приложения): «Все пользователи» 6, администраторы приложения 1, главные аналитики 1, руководители 1, операторы 3.

### 12. Новые договоры по типам абонентов — итоговый с условием на данные

- **Потребность.** Отчёт «Статистика» → «Новые договоры по типам абонентов» (навигация макета `Stats.dc.html`, 5.4 ПЗ): сколько договоров заключено в каждом месяце (квартале, году) периода, ряд диаграммы на каждый тип абонента, выгрузка в Excel.
- **Кто.** Руководитель — свой провайдер; главный аналитик — все или выбранный (отбор «Провайдер» макета).
- **Объект.** `api.report_new_contracts(p_from, p_to, p_grain, p_provider_id)`.
- **Таблицы.** `core.contract` ⋈ `core.subscriber` ⋈ `ref.subscriber_type`.
- **Почему этот тип.** Результат — количества по паре (период, тип), значит группировка; отбор строк по периоду и провайдеру — условие на данные (`WHERE`). Условия на группы нет: показываются все типы, даже с одним договором. Проще некуда: без группировки нет количеств, без `WHERE` нет периода.
- **Для ТЗ курсовой, п. 5 (не задание ЛР 6): по значению, с использованием индекса и без.** `provider_id = …` и `connected_on BETWEEN …` идут по индексу `ix_contract_provider_id_connected_on`. Проверено 07.10 (`labs/lab06/explain/q12_index.txt`, `q12_noindex.txt`): руководитель «ДонНет», III квартал 2026, по месяцам — Bitmap Index Scan; главный аналитик, все провайдеры, 2024–2025 годы по годам (8 714 договоров из 12 002, 73 %) — Seq Scan. Эти два набора параметров и показываются как «с использованием индекса / без использования» — планами этого же запроса, без отдельного искусственного запроса. За один 2025 год (37 % договоров) таблица маленькая, и планировщик ещё выбирает битовую карту — параметры демонстрации фиксируются.
- **Нулевые точки.** Пара (период, тип) без договоров строки не даёт; на диаграмме это ноль — его ставит клиент при построении ряда. Заполнение на сервере потребовало бы декартова произведения периодов и типов с левым соединением, а таблице и Excel пустые строки не нужны.

```sql
SELECT date_trunc(p_grain, c.connected_on)::date AS period, st.name AS subscriber_type, count(*) AS contracts
FROM core.contract c
JOIN core.subscriber s      ON s.id = c.subscriber_id
JOIN ref.subscriber_type st ON st.id = s.subscriber_type_id
WHERE c.provider_id = ANY (v_scope) AND c.connected_on BETWEEN p_from AND p_to
GROUP BY 1, st.id, st.name
ORDER BY 1, st.id;
```

### 13. Общие абоненты — итоговый с условием на группы

Аналог прежнего запроса «Абоненты нескольких провайдеров» того же вида (решение студента 07.10: прежний запрос из рабочих экранов макета не следовал, «придумай аналог»).

- **Потребность.** По D25 сведения абонента, которого обслуживают несколько провайдеров, меняет только администратор приложения (`sec.check_subscriber_edit`): оператор получает отказ «сведения реестра меняет администратор» и обращается к нему. Найти таких абонентов администратору сейчас негде. Новый экран в навигации администратора: «Справочники» → «Общие абоненты» (в макете ЛР 4 его нет — запись в `docs/ui/deviations.md`).
- **Кто.** Только администратор приложения. Договоры ему недоступны (D25), поэтому выводится только число провайдеров, без их названий.
- **Объект.** `api.q_shared_subscribers(p_min_providers DEFAULT 2, p_limit, p_offset)`: абонент, тип, город, адрес, телефон, провайдеров. Порог по умолчанию 2 — ровно правило D25; 3 и больше — абоненты, общие для многих провайдеров. Порог меньше 2 — ошибка.
- **Таблицы.** `core.subscriber` ⋈ `ref.subscriber_type` ⋈ `ref.city` ⋈ `core.contract`.
- **Почему этот тип.** «Провайдеров не меньше N» — условие на группу договоров абонента, а не на отдельную строку: `WHERE` его не выразит, нужен `HAVING`. Условия на данные нет: как и в правиле D25, учитываются расторгнутые договоры. Группировка — в самом запросе, по первичным ключам; вынесенная в подзапрос по одной таблице, она читалась бы как «запрос на запросе». Сейчас 590 общих абонентов, из них 29 — у трёх провайдеров и больше.
- **Проверка.** Список совпадает с расчётом суперпользователя (12.3); порог — параметр (12.3а); у оператора «ДонНет» закрыто для изменения ровно столько абонентов, сколько общих абонентов у «ДонНет» (12.4) — запрос и правило D25 считают одно и то же.

```sql
SELECT s.id, s.name, st.name, ci.name, s.address, s.phone, count(DISTINCT c.provider_id) AS providers
FROM core.subscriber s
JOIN ref.subscriber_type st ON st.id = s.subscriber_type_id
JOIN ref.city ci            ON ci.id = s.city_id
JOIN core.contract c        ON c.subscriber_id = s.id
GROUP BY s.id, st.id, ci.id
HAVING count(DISTINCT c.provider_id) >= p_min_providers
ORDER BY s.name, s.id;
```

### 14. Договоры без сеансов больше N дней — итоговый с условием на данные и на группы

- **Потребность.** Счётчик «Договоры без сеансов более 30 дней» у оператора и руководителя (`api.home_todo`, есть) открывает список: какие договоры и сколько простаивают. Месяц простоя (отпуск) и два года (брошенный договор, кандидат на расторжение) решаются по-разному, поэтому дата последнего сеанса в списке обязательна.
- **Кто.** Оператор, руководитель (свой провайдер).
- **Объект.** `api.q_idle_contracts(p_days DEFAULT 30, p_limit, p_offset)`: номер договора, абонент, телефон, дата подключения, последний сеанс (пусто — сеансов не было), дней без сеансов.
- **Таблицы.** `core.contract` ⋈ `core.subscriber` ⟕ `core.session`.
- **Почему этот тип.** «Последний сеанс» — `max(started_at)` по договору, значит группировка нужна уже для вывода; «последний сеанс раньше даты» — условие на группу (`HAVING`); «договор действует, свой провайдер, заключён раньше N дней назад» — условия на строки (`WHERE`). Счётчик сейчас считает через `NOT EXISTS`, но `NOT EXISTS` даёт только множество договоров, без даты — для списка понадобился бы второй коррелированный подзапрос.
- **Счётчик = список.** Сейчас счётчик режет по `now() - interval '30 days'` (граница плывёт в течение дня) и не исключает свежие договоры — с этим условием числа расходятся на 1–2 у 18 из 31 провайдера (проверено). Граница одна — `current_date - p_days`, и договор, заключённый вчера, ещё не простаивает. Надёжнее всего счётчику брать `total_count` из самой функции — тогда расхождение невозможно.

```sql
SELECT c.contract_no, s.name, c.connected_on, max(se.started_at) AS last_session
FROM core.contract c
JOIN core.subscriber s    ON s.id = c.subscriber_id
LEFT JOIN core.session se ON se.contract_id = c.id
WHERE c.provider_id = ANY (v_scope) AND c.closed_on IS NULL
  AND c.connected_on < current_date - p_days
GROUP BY c.id, s.id
HAVING max(se.started_at) IS NULL                      -- сеансов не было
    OR max(se.started_at) < current_date - p_days       -- или последний — до границы
ORDER BY last_session NULLS FIRST;
```

### 15. Выручка по периодам — объединение (UNION) и запрос на запросе по принципу итогового

- **Потребность.** Главный отчёт «Статистика» → «Выручка по периодам» (макет `Stats.dc.html`): по месяцам — новых договоров, трафик, подключения, выручка, строка «Итого», отбор «Тип абонента», диаграмма «Оплата трафика» + «Подключения». То же определение выручки — у счётчика «Выручка за месяц».
- **Кто.** Руководитель (свой провайдер), главный аналитик (все или выбранный).
- **Объекты.**
  - **15а** `api.v_revenue_items` — представление без параметров: доходные операции. Плата за подключение договора (дата — `connected_on`) и оплата трафика сеанса (дата — `started_at`); колонки: провайдер, абонент, тип абонента, дата-время, вид, сумма, Мб. Объединение `UNION ALL`. На нём же — отчёты 17 и «Крупнейшие абоненты» (по абоненту).
  - **15б** `api.report_revenue(p_from, p_to, p_grain, p_provider_id, p_subscriber_type_id)` — итоговый запрос к 15а, `GROUP BY ROLLUP (период)`.
- **Почему этот тип.** У выручки два источника с разными датами: плата за подключение — одна на договор, в месяце заключения; трафик — в месяцах сеансов. Соединение договора с сеансами повторило бы плату за подключение на каждом сеансе и потеряло бы договоры без сеансов. Поэтому строки двух источников объединяются — `UNION ALL`: одинаковые суммы — разные операции, удалять «дубли» нельзя (в принятом наборе колонок — провайдер, абонент, тип, дата-время, вид, сумма, Мб — совпадающих строк сейчас нет, `UNION` дал бы те же 112 027 строк; но две одинаковые оплаты одного абонента в одну секунду допустимы, и `UNION` занизил бы выручку; тест 12.9 сверяет число строк с числом договоров и сеансов), сортировка для `UNION` не нужна. Итоги считаются уже по объединению — запрос на запросе. Без внутреннего запроса пришлось бы считать итоги каждого источника отдельно и соединять их по периоду (`FULL JOIN`) — сложнее.
- **Проверено на копии.** Условия отчёта проталкиваются в обе ветви объединения: сеансы — по `ix_session_started_at`, договоры — по `provider_id`; 9 месяцев одного провайдера — 17 мс. В ветви договоров дата приводится к `timestamptz`, индекс по `connected_on` не используется: договоров на порядок меньше, чем сеансов, а отбор по провайдеру идёт по первой колонке индекса.
- **Тот же итог.** Отчёт за месяц совпадает со счётчиком «Выручка за месяц» (октябрь 2026, провайдер 1: 5 962,73 — проверено) — тест.
- **Месяцы без операций** строк не дают (на реальных данных такого не бывает: сеансы идут каждый день); на диаграмме — ноль, как в 12.

```sql
-- 15а: доходные операции (видимость — как в представлениях ЛР 5: функция вызывается один раз)
SELECT c.provider_id, c.subscriber_id, s.subscriber_type_id, c.connected_on::timestamptz AS at,
       'подключение' AS kind, c.connection_fee AS amount, 0 AS volume_mb
FROM core.contract c JOIN core.subscriber s ON s.id = c.subscriber_id
WHERE c.provider_id = ANY ((SELECT sec.scope_data()))
UNION ALL
SELECT c.provider_id, c.subscriber_id, sb.subscriber_type_id, se.started_at, 'трафик', se.cost, se.volume_mb
FROM core.session se
JOIN core.contract c    ON c.id = se.contract_id
JOIN core.subscriber sb ON sb.id = c.subscriber_id
WHERE c.provider_id = ANY ((SELECT sec.scope_data()));

-- 15б: итоги по периодам
SELECT date_trunc(p_grain, r.at)::date AS period,                 -- NULL — строка «Итого»
       count(*) FILTER (WHERE r.kind = 'подключение')        AS new_contracts,
       sum(r.volume_mb)                                       AS volume_mb,
       sum(r.amount) FILTER (WHERE r.kind = 'подключение')   AS connection_fees,
       sum(r.amount)                                          AS revenue
FROM api.v_revenue_items r
WHERE r.at >= p_from AND r.at < p_to + 1
  AND (p_provider_id IS NULL OR r.provider_id = p_provider_id)
  AND (p_subscriber_type_id IS NULL OR r.subscriber_type_id = p_subscriber_type_id)
GROUP BY ROLLUP (1)
ORDER BY 1 NULLS LAST;
```

### 16. Провайдеры без сотрудников — подзапрос с NOT IN

- **Потребность.** Счётчик администратора «Провайдеры без сотрудников» (сейчас 29) открывает «Провайдеры» — список должен показать именно их, чтобы завести операторов и руководителей.
- **Кто.** Администратор приложения.
- **Объект.** Параметр `p_without_staff boolean` у `api.q_providers` (запрос 10, экран тот же; по образцу отбора `p_without_new`).
- **Почему этот тип.** Нужны провайдеры, которых нет во множестве «провайдеры сотрудников», — разность множеств. Колонки сотрудников не нужны, подзапрос не зависит от строки провайдера и вычисляется один раз (hashed SubPlan). Отбор необязательный — включается флажком в уже существующем запросе 10: условие `NOT IN` в `WHERE` включается и выключается параметром, не трогая `FROM`. Левое соединение с `sec.app_user` и `IS NULL` дало бы тот же отбор, но при выключенном флажке размножило бы строки списка — по строке на сотрудника.
- **Счётчик = список.** Счётчик «Провайдеры без сотрудников» сейчас считает через `NOT EXISTS`; переписать тем же условием (или брать `total_count` списка) и проверить тестом.
- **Ловушка NOT IN и NULL.** У администраторов и главных аналитиков `provider_id IS NULL`; без `WHERE u.provider_id IS NOT NULL` в подзапросе выражение `p.id NOT IN (…, NULL)` никогда не истинно и список пуст (проверено: 0 строк вместо 29). Пункт для защиты и отдельный тест.

```sql
  AND (NOT p_without_staff
       OR p.id NOT IN (SELECT u.provider_id FROM sec.app_user u WHERE u.provider_id IS NOT NULL))
```

### 17. Доли провайдеров: первые N и «Прочие» — подзапрос с CASE, операции над итоговыми данными

- **Потребность.** «Выручка по периодам» у главного аналитика (макет `Stats_Chief`): ряды диаграммы — четыре крупнейших провайдера и «Прочие (27 провайдеров)», таблица «Провайдер / Договоров / Трафик / Выручка / Доля, %» с «Итого». 31 ряд на диаграмме не читается — отсюда «первые N и прочие». На начальной странице аналитика есть ссылка «Доли провайдеров».
- **Кто.** Главный аналитик.
- **Объект.** `api.report_provider_shares(p_from, p_to, p_top DEFAULT 4, p_grain DEFAULT 'month')`: строки без периода — таблица по группам провайдеров с «Итого», строки с периодом — точки рядов диаграммы (с `p_grain IS NULL` — только таблица); подпись «Прочие (27 провайдеров)» формирует сервер.
- **Колонка «Договоров»** — действующие на конец периода, а не новые: в макете сумма столбца (1 690 + 1 402 + 1 214 + 905 + 5 651 = 10 862) равна счётчику аналитика «Действующих договоров». Считается отдельным подзапросом по договорам, сгруппированным по провайдеру до соединения.
- **Почему этот тип.** Подпись группы («ООО «…»» или «Прочие») зависит от места провайдера по выручке, а место — от итога по провайдеру. Сгруппировать по месту собственного итога в одном запросе нельзя. Внутренний запрос считает выручку провайдера, его место и общий итог (`row_number()`, `sum(…) OVER ()` — операции над итоговыми данными), внешний — `CASE WHEN rnk <= p_top THEN … ELSE 'Прочие' END` и повторную группировку; доля — выручка группы / общий итог × 100.
- **Детали.** Место — `row_number()` (при равной выручке `rank()` дал бы больше N названий), по итогу за весь период: для рядов по месяцам внутренний запрос тот же, а строки 15а соединяются с ним по провайдеру и группируются по (группа, период) — иначе первые N были бы свои в каждом месяце. Провайдеры берутся из `api.v_providers` с левым соединением — провайдер без выручки в периоде попадает в «Прочие» (в макете «Прочие (27 провайдеров)» при 31). Название — `display_name` («ООО «…»»), группировка — по коду провайдера. Доли в сумме после округления могут дать 100,1 — тест сравнивает до округления.

```sql
SELECT CASE WHEN x.rnk <= p_top THEN x.display_name ELSE 'Прочие' END AS provider_group,
       count(*) AS providers, sum(x.new_contracts) AS new_contracts,
       sum(x.volume_mb) AS volume_mb, sum(x.revenue) AS revenue,
       round(100 * sum(x.revenue) / max(x.total), 1) AS share_pct
FROM (SELECT p.id, p.display_name,
             count(r.kind) FILTER (WHERE r.kind = 'подключение')                AS new_contracts,
             coalesce(sum(r.volume_mb), 0)                                       AS volume_mb,
             coalesce(sum(r.amount), 0)                                          AS revenue,
             row_number() OVER (ORDER BY sum(r.amount) DESC NULLS LAST, p.id)   AS rnk,   -- без выручки — в конец
             sum(sum(r.amount)) OVER ()                                          AS total
      FROM api.v_providers p
      LEFT JOIN api.v_revenue_items r ON r.provider_id = p.id AND r.at >= p_from AND r.at < p_to + 1
      GROUP BY p.id, p.display_name) x
GROUP BY ROLLUP (1)
ORDER BY grouping(CASE WHEN x.rnk <= p_top THEN x.display_name ELSE 'Прочие' END), min(x.rnk);  -- «Итого» последней
```

Проверено на копии (январь–сентябрь 2026, `p_top = 4`): четыре провайдера по 3,5–3,9 %, «Прочие» (27 провайдеров) — 85,3 %, «Итого» (31) — 100 %. Провайдеры генератора почти равны по размеру, поэтому «Прочие» велики; на реальных данных и в макете доля первых больше — `p_top` задаётся в отчёте.
