# Требования к разрабатываемому ПО

Основано на: `docs/task/variant.md`, `docs/task/coursework-requirements.md`, анализе `docs/analysis/domain.md`.
Архитектура: **толстая БД / тонкий клиент**. Всё, что можно проверить или посчитать в PostgreSQL, делается там. Клиент на Qt/C++ только подключается, вызывает функции схемы `api` и показывает результат.

## 1. Архитектура

```
Qt-клиент (C++/Qt 6, QPSQL)
   │  подключение под личным логином PostgreSQL
   ▼
schema api   — функции SECURITY DEFINER, единственное, что видят пользователи (GRANT EXECUTE группам)
   │  проверка группы, валидация, бизнес-правила, пагинация
   ▼
schema core  — основные таблицы (RLS ENABLE + FORCE), триггеры
schema ref   — справочники
schema sec   — привязка логинов к провайдерам, вспомогательные функции ролей
schema audit — журнал изменений (jsonb)
```

Владелец всех объектов — роль `app_owner` (NOLOGIN, не суперпользователь, CREATEROLE). Пользовательские группы не имеют прав на таблицы вообще — только `USAGE` на схему `api` и `EXECUTE` на конкретные функции.

## 2. Роли

| Группа PostgreSQL | Кто | Привязка к провайдеру | Видимость строк |
|---|---|---|---|
| `grp_admin` | Администратор приложения (D26) | нет | справочники, провайдеры, пользователи — операторы, руководители, главные аналитики; оперативные данные не нужны → не показываются |
| `grp_dba` | Администратор БД (D26) | нет | пользователи — администраторы приложения; журнал изменений, таблицы, подключения; через `api` данных приложения не видит; чтение таблиц (`pg_read_all_data`) — только для резервных копий, структура — через `SET ROLE app_owner` |
| `grp_operator` | Оператор (сотрудник провайдера) | обязательна | только абоненты/договоры/сеансы своего провайдера |
| `grp_manager` | Руководитель провайдера | обязательна | статистика и данные своего провайдера, только чтение |
| `grp_chief` | Главный аналитик объединения («председатель») | нет | сводная статистика по всем провайдерам, только чтение |

Правила (из методички, обязательны):
- Пользователь = LOGIN-роль PostgreSQL, член ровно одной группы. Пароли хранит только PostgreSQL.
- Группа определяется функцией `sec.current_group()` по прямому членству `session_user` в группе (`sec.group_of`, системный каталог `pg_auth_members`), а не по полю таблицы. `pg_has_role(…, 'MEMBER')` не подходит: учитывает и косвенное членство (D26).
- `sec.app_user(login, full_name, provider_id)` хранит только привязку к провайдеру и ФИО.
- Клиент строит интерфейс **после** успешного подключения по результату `api.whoami()` → (логин, ФИО, группа, провайдер). Скрытие кнопок на клиенте — удобство; реальный запрет — в БД.

## 3. Разграничение доступа на уровне строк (RLS)

- `ALTER TABLE core.* ENABLE ROW LEVEL SECURITY; ALTER TABLE core.* FORCE ROW LEVEL SECURITY;` — FORCE обязателен, иначе функции SECURITY DEFINER владельца обходят политики.
- В политиках используется `session_user` (внутри SECURITY DEFINER `current_user` = владелец).
- `core.contract`, `core.session`: оператор/руководитель — `provider_id = sec.current_provider_id()`; chief — все; admin — нет доступа.
- `core.subscriber` (общий реестр, D25): оператор/руководитель видят абонента, если у их провайдера есть договор с ним (`EXISTS` договора с `provider_id = sec.current_provider_id()`); chief и admin — весь реестр (admin — без договоров и сеансов). Поиск дубликата — по точному наименованию и телефону во всём реестре (`api.subscriber_find_exact(name, phone)`), возвращает только тип и город; договор с найденным абонентом присоединяет его, а не создаёт копию (`api.contract_create`). Сведения реестра меняет оператор — только у абонента без договоров других провайдеров; общего абонента — admin; удалить общего абонента нельзя.
- `core.provider`: все видят справочную карточку; изменять — только admin.
- Проверка RLS — тестами в `db/tests/` с `SET SESSION AUTHORIZATION`.

## 4. Функции схемы `api` (план)

Соглашения: `api.<сущность>_list(фильтры…, p_search text, p_limit int, p_offset int)` → `TABLE(…, total_count bigint)`; `_get(id)`, `_create(…) → id`, `_update(id, …, p_row_version) → новый row_version`, `_delete(id)`. Ошибки — `RAISE EXCEPTION USING ERRCODE = 'P0001', MESSAGE = '<текст для пользователя на русском>'`.

| Область | Функции | Группы |
|---|---|---|
| Сессия | `whoami()` | все |
| Пользователи | `q_users`, `user_create(login, full_name, group, provider_id)`, `user_set_login(login, enabled)`, `user_reset_password(login)` → временный пароль, `change_own_password(new)` (D27, миграция 075); план: `user_update` | admin — операторы, руководители, аналитики; dba — администраторы приложения (D26) |
| База данных | `q_change_log(from, to, table, operation, db_user)`, `db_tables()`, `db_connections()` | dba |
| Справочники | `ownership_type_*`, `city_*`, `subscriber_type_*`, `tariff_*` | admin (CRUD); остальным `*_lookup()` для выпадающих списков |
| Провайдеры | `provider_list`, `provider_get`, `provider_create/update/delete` | admin CRUD; остальные list/get |
| Абоненты | `q_subscribers`, `v_subscribers`, `subscriber_find_exact`, `subscriber_update/delete` (абонент создаётся в `contract_create`) | operator — свои не общие; admin — изменение любого (D25); manager/chief чтение |
| Договоры | `q_contracts(p_subscriber_id, p_active_only, …)`, `v_contracts`, `contract_create/update` (расторжение — `closed_on` в `contract_update`) | operator; manager/chief чтение |
| Сеансы | `session_list(p_contract_id, p_from, p_to, …)`, `session_create(contract_id, started_at, volume_mb, tariff_id default null)`, `session_delete` | operator; manager/chief чтение |
| Отчёты | `report_revenue(p_from, p_to, p_grain, p_provider_id, p_subscriber_type_id)`, `report_provider_shares(…)` (chief), `q_tariff_usage(…)` (запрос 9), `report_new_contracts(…)`, `report_top_subscribers(…)` — план ЛР 6 (D28, `queries-plan.md`) | manager (свой провайдер), chief (все / фильтр) |
| Запросы ЛР 5–6 | функции `q_*` с параметрами и представления `v_*` без параметров | manager, chief |

Все функции: `SECURITY DEFINER`, `SET search_path = pg_catalog, pg_temp`, полностью квалифицированные имена объектов, первая строка тела — проверка группы.

## 5. Триггеры (не менее 6 типов событий на ≥ 2 таблицах)

| Событие | Таблица | Назначение |
|---|---|---|
| BEFORE INSERT | `core.session` | проверить дату относительно договора; подобрать тариф по времени, если не задан; зафиксировать скидку и рассчитать стоимость |
| AFTER INSERT | `core.contract` | запись в `audit.change_log` (new как jsonb) |
| BEFORE UPDATE | `core.contract` | запретить смену абонента/провайдера; `row_version := row_version + 1`; проверить конфликт версии |
| AFTER UPDATE | `core.contract` | журнал: old/new jsonb |
| BEFORE DELETE | `core.provider` | запретить удаление при сеансах за последние 12 месяцев |
| AFTER DELETE | `core.contract` | журнал: old jsonb |
| INSTEAD OF INSERT/UPDATE/DELETE | `api.v_contract_card` (абонент + договор) | модифицируемое представление |

## 8. Клиентское приложение (Qt 6 / C++)

Окно входа: сервер, порт, база, логин, пароль → `QSqlDatabase("QPSQL")` → `api.whoami()`.
Главное окно — набор страниц; видимость страниц и кнопок по группе:

| Страница | admin | operator | manager | chief |
|---|---|---|---|---|
| Провайдеры | CRUD | просмотр своей карточки | просмотр своей | просмотр всех |
| Абоненты и договоры (составная форма абонент → договоры → сеансы) | — | CRUD | чтение | чтение |
| Сеансы (журнал с фильтром по периоду) | — | ввод, удаление | чтение | чтение |
| Статистика (фильтры, группировка месяц/квартал/год, диаграмма, экспорт в Excel) | — | — | свой провайдер | все + фильтр по провайдеру |
| Запросы (результаты запросов ЛР 5–6) | — | — | да | да |
| Справочники | CRUD | — | — | — |
| Пользователи (исключительная тематика админа) | CRUD | — | — | — |

Администратор БД (D26): «Пользователи» (только администраторы приложения), «Журнал изменений», «Таблицы», «Подключения»; остальных страниц у него нет.

Общие требования к клиенту:
- Одна программа для всех ролей; одна страница на тему, инструменты по роли.
- Пагинация: выбор 20 / 100 / 200, «страница X из Y» по `total_count`.
- ID не выводятся; хранятся в `Qt::UserRole` модели или скрытых колонках. Пользователь видит номер договора, наименования.
- Поиск и фильтрация — параметрами серверных функций, не на клиенте.
- Экспорт в Excel — библиотека QXlsx; диаграммы — Qt Charts (или Qt Graphs, в зависимости от версии Qt).
- Никакого SQL, кроме `SELECT * FROM api.f(:p1, …)` через `QSqlQuery::prepare` + `bindValue`; конкатенация строк в SQL запрещена.
- Пароль не хранится; в `client/config.ini` только сервер, порт, база, последний логин.
- Обработка ошибок: текст `RAISE EXCEPTION` показывается пользователю; конфликт версии → предложение перечитать запись.

## 9. Нефункциональные требования

- PostgreSQL 16+ (рекомендуется 17): изменения CREATEROLE в 16 влияют на управление пользователями из функций.
- Qt 6.5+, CMake, компилятор MSVC или MinGW. На Windows рядом с исполняемым файлом нужны `libpq.dll` и её зависимости, иначе плагин QPSQL не загрузится.
- Кодировка БД UTF8, локаль ru_RU.
- Страница списка ≤ 1 с на 200 000 сеансах (индексы, отсечение секций).
- Все SQL-скрипты идемпотентно пересобирают БД с нуля: `db/build.sql`.

## 10. План тестирования (раздел 6 ПЗ)

| № | Проверка | Ожидается |
|---|---|---|
| T1 | Оператор делает `SELECT * FROM core.contract` | `permission denied` |
| T2 | Оператор провайдера A запрашивает договор провайдера B через `api.contract_get` | пусто / ошибка «не найдено» |
| T3 | Оператор вызывает `api.user_create` | `permission denied for function` |
| T4 | Руководитель вызывает `api.contract_update` | отказ |
| T5 | Два клиента редактируют один договор | второй получает конфликт `row_version` |
| T6 | Удаление абонента | каскадно удалены договоры и сеансы (подсчёт до/после) |
| T7 | Удаление провайдера с недавними сеансами | отказ триггера |
| T8 | Сеанс раньше даты подключения | отказ триггера; тариф подобран автоматически; стоимость рассчитана |
| T9 | Ввод `' OR 1=1 --` в поиск | обычный поиск без побочных эффектов |
| T10 | EXPLAIN запроса за квартал по `core.session` | отсечение секций |
