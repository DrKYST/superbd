# Сброс пароля: временный пароль и смена при входе (D27, план)

Статус: сервер реализован 2026-10-07 (`db/migrations/075_password_reset.sql`, тесты 11.1–11.8 — `db/tests/070_password_reset.sql`), D27 принято; формы клиента «Временный пароль» и «Смена пароля» — после артбордов макета. Основа — разделение администраторов (D26).

Отличия реализации от плана: колонки `sec.app_user` названы `reset_pending`, `reset_at`, `reset_by` (тест 1.3 запрещает колонки с «passw» в имени — защита от таблицы паролей); проверка флага — функция `sec.assert_password_changed()` (вызывают `sec.require_group`, `sec.provider_scope` и представления `api.v_user_groups`, `api.v_manageable_groups`); проверка группы без флага — `sec.check_group` (для `whoami` и `change_own_password`). До форм клиент при входе с временным паролем показывает сообщение и не открывает главное окно; созданному в клиенте пользователю пароль не показывается — нужно окно «Временный пароль».

## Задача

Администратор сбрасывает пароль сотрудника и получает временный пароль. С временным паролем сотрудник может только войти и задать свой: пока он этого не сделал, остальные функции приложения ему недоступны. Пароли по-прежнему хранит только PostgreSQL (правило 2 `CLAUDE.md`); временный пароль нигде в таблицах не записывается и показывается администратору один раз.

## Кто кому сбрасывает

Как при управлении учётными записями (D26):

| Кто | Кому |
|---|---|
| Администратор приложения | операторам, руководителям, главным аналитикам |
| Администратор БД | администраторам приложения |
| `postgres` (`\password` в psql) | администраторам БД — приложение не имеет права ADMIN на их роли (D26) |

Себе пароль не сбрасывают — для этого есть «Сменить пароль».

## Сервер

1. **Строка сотрудника `sec.app_user`** — три новые колонки: `must_change_password boolean NOT NULL DEFAULT false`, `password_reset_at timestamptz`, `password_reset_by text`. Самого пароля в них нет: он только в `pg_authid`.
2. **`api.user_reset_password(p_login text) RETURNS text`** (SECURITY DEFINER, `grp_admin`, `grp_dba`):
   - проверки — как в `api.user_set_login`: учётная запись управляемой группы, не своя;
   - временный пароль генерирует сервер: 12 символов из алфавита без похожих знаков (нет `0/O`, `1/l/I`), источник случайности — `gen_random_uuid()` (криптостойкий генератор, есть без расширений с PostgreSQL 13);
   - `ALTER ROLE … PASSWORD '<временный>' VALID UNTIL now() + interval '1 day'` — неиспользованный временный пароль сервер перестаёт принимать через сутки; хранится он, как любой пароль, хешем SCRAM (`password_encryption = scram-sha-256`);
   - `must_change_password = true`, кто и когда сбросил;
   - право входа не меняется: заблокированный (`NOLOGIN`, D26) остаётся заблокированным;
   - пароль возвращается результатом функции — один раз.
3. **`api.change_own_password(p_new text)`** (SECURITY DEFINER, все группы, кроме `grp_dba`):
   - правила пароля на сервере: не короче 8 символов, не совпадает с логином;
   - `ALTER ROLE session_user PASSWORD p_new VALID UNTIL 'infinity'`, флаг снимается;
   - та же функция — для обычной смены пароля по ссылке «Сменить пароль» начальной страницы.
   Администратор БД меняет свой пароль через `\password`: роль может сменить свой пароль сама, но срок действия (`VALID UNTIL`) снять не может, а у `app_owner` нет права ADMIN на роли администраторов БД.
4. **Принуждение — на сервере, не только в клиенте.**
   - `api.whoami()` возвращает `must_change_password`; клиент по нему открывает форму смены пароля.
   - `sec.require_group` (первая строка каждой функции `api`) и функции области видимости `sec.scope_data` / `sec.scope_providers` (через них читают представления `api.v_*`) отказывают, пока флаг стоит. Исключения — `whoami` и `change_own_password`. Код ошибки — отдельный (например, `SB001`), чтобы клиент отличил «смените пароль» от «нет прав» (`42501`).
5. **Создание пользователя.** `api.user_create` сразу выдаёт временный пароль — возвращает `(id, temp_password)`; отдельного шага «задать пароль» нет. Сейчас пользователь создаётся без пароля и войти не может, пока пароль не задан.
6. **Журнал.** В `audit.change_log` (D10) попадёт изменение строки `sec.app_user` — флаг, кто и когда; пароля там нет.

## Клиент

- **«Пользователи».** Кнопка макета «Сменить пароль…» становится «Сбросить пароль…»: подтверждение → окно с временным паролем (крупно, моноширинным шрифтом), кнопка «Копировать», текст «Пароль показан один раз и действует сутки. Передайте его сотруднику лично; при входе он задаст свой». После закрытия окна пароль не восстановить — только сбросить ещё раз.
- **«Пользователь (создание)».** Группа «Пароль» макета заменяется надписью «Временный пароль будет показан после записи»; после записи — то же окно с паролем.
- **После входа.** Если `must_change_password` — модальная форма «Смена пароля» (новый пароль, повтор) до главного окна; «Отмена» — выход из программы. Та же форма открывается по ссылке «Сменить пароль».
- **Окно входа.** При ошибке «password authentication failed» — подсказка «Если вам выдали временный пароль больше суток назад, попросите администратора сбросить пароль ещё раз».
- **Макет.** Нужны два артборда — «Временный пароль» и «Смена пароля»; по правилу `ui-spec.md` сначала макет, потом формы Qt.

## Безопасность

- Временный пароль генерирует и сразу хеширует сервер; в таблицах проекта его нет.
- Пароль не должен попасть в журнал сервера. Вызовы `SELECT api.…` не пишутся при `log_statement` = `none`, `ddl` или `mod`. Новый пароль в `change_own_password` передаётся параметром запроса: значения параметров не пишутся при `log_parameter_max_length = 0` (по умолчанию пишутся, если сработал `log_min_duration_statement`) — добавить в `docs/server-config.md`. При ошибке внутри `EXECUTE` текст оператора попадает в контекст ошибки, поэтому `ALTER ROLE` выполняется последним, после всех проверок.
- По сети пароль идёт так же, как при обычном входе: на удалённом сервере нужен `sslmode=require` в `config.ini` клиента.
- **Альтернатива отвергнута:** хеш SCRAM на клиенте (`PQencryptPasswordConn`, как делает `\password` в psql). Пароль не уходил бы на сервер открытым, но правила пароля пришлось бы проверять в клиенте — нарушение «вся логика на сервере».

## Тесты (план, 11.x)

1. Администратор приложения сбрасывает пароль оператору: 12 символов, `rolvaliduntil` ≈ сейчас + сутки, флаг, кто и когда.
2. Себе, администратору приложения и администратору БД — отказ; администратор БД сбрасывает администратору приложения, но не оператору.
3. С флагом: `whoami` работает и сообщает флаг; `q_contracts` и `v_subscribers` — отказ с кодом смены пароля.
4. `change_own_password`: короткий пароль — отказ (`22023`); правильный — флаг снят, срок `infinity`, функции снова работают.
5. Временного пароля нет ни в одной колонке `sec.app_user` и `audit.change_log`.
6. Сброс заблокированному — вход по-прежнему запрещён.
7. Пользователь, созданный `user_create`, сразу с флагом и сроком временного пароля.
