# Задача: запросы ТЗ курсового проекта (17–23) и сквозная нумерация

Решение студента от 29.10.2026. Записать его как D31: оно пересматривает D28 в части «виды ТЗ, которые уже получились в других запросах, новыми запросами не дублировать».

## Зачем

В ТЗ курсового проекта, п. 5 (`docs/task/coursework-requirements.md`), есть виды запросов, которых нет в заданиях ЛР 5 и ЛР 6 (`docs/task/labs.md`). Сейчас они закрыты попутно (D28): «по маске» и `IN` — запросом 8, «всего / в том числе» — запросом 11, «с использованием индекса / без использования индекса» — двумя планами запроса 12. Нужно, чтобы у каждого такого вида был свой запрос со своим номером. Нумерация сквозная: сначала запросы ЛР 5, затем ЛР 6, затем ТЗ курсового проекта.

## 2. Новые запросы

Общее для всех, как в 060/061 и `.claude/rules/sql.md`: `SECURITY DEFINER`, `SET search_path = pg_catalog, pg_temp`, `SET TimeZone = 'Europe/Moscow'` (D19), первой строкой `sec.require_group(…)`. Видимость — через `sec.scope_data(p_provider_id)`: руководитель видит своего провайдера, главный аналитик — всех или выбранного. У отчётов — `sec.check_report_period`, граница периода `< p_to + 1`. У списков `q_*` — `p_limit`, `p_offset`, `total_count`. Данные берутся из нескольких таблиц, условия задаются только параметрами, регулярных выражений нет (D24). `COMMENT ON` — «Запрос N (ТЗ курсового проекта). …». `EXECUTE` — только названным группам. Новая миграция — `db/migrations/062_queries_coursework.sql`, в `db/build.sql` после 061.

### 17. Абоненты и договоры по типам: всего и в том числе — `api.v_subscriber_type_totals`

- Параметров нет, поэтому это представление.
- Строки: «Всего»; «в том числе юридические лица», под ней типы с `is_legal = true` (школа, колледж, …); «в том числе физические лица», под ней частное лицо и ИП. Группировка — `GROUP BY ROLLUP (st.is_legal, st.name)` или `GROUPING SETS`. Подпись строки и порядок (колонка `sort_order`) формирует сервер.
- Колонки: абонентов; договоров всего; в том числе действующих (`count(*) FILTER (WHERE c.closed_on IS NULL)`). Так «всего / в том числе» есть и в строках, и в колонках.
- Таблицы: `ref.subscriber_type`, `core.subscriber`, левое соединение с `core.contract` (у аналитика есть абоненты без договоров).
- Видимость — как в запросах 6 и 8 (D25): руководителю — абоненты с договором его провайдера и только договоры этого провайдера; аналитику — весь реестр.
- Группы: руководитель, главный аналитик.
- Чем отличается от 11: там один уровень и одна итоговая строка, здесь два уровня «в том числе» и итоги в колонках.

### 18. Трафик абонентов по маске наименования — `api.q_subscriber_traffic(p_mask, p_from, p_to, p_provider_id DEFAULT NULL, p_limit, p_offset)`

- Формулировка взята из утверждённого макета ЛР 4 (`docs/ui/mockup/Queries.dc.html`, список запросов).
- Маска: `*` — любые символы, `?` — один символ; введённые `%`, `_`, `\` — обычные символы. Нужна новая функция `sec.like_mask(text)` по образцу `sec.like_prefix` (057): экранирование, замена `*` → `%` и `?` → `_`, нижний регистр. Условие — `lower(s.name) LIKE sec.like_mask(p_mask)`. Пустая маска — ошибка с понятным текстом.
- Итоговый запрос: по абоненту — тип, договоров, сеансов, Мб и сумма за период. «Итого» — оконными суммами, как в запросах 2–3; плюс `total_count`.
- Таблицы: абонент ⋈ тип абонента ⋈ договор ⋈ сеанс.
- Пример для плана и снимка: маска `*школа*`, январь–сентябрь 2026, руководитель «ДонНет».
- Чем отличается от поиска в запросе 8: там «начинается с» по индексу, здесь подстановочные символы стоят где угодно. Индекс не используется, это нормально — так и написать в README.
- Группы: руководитель, главный аналитик.

### 19. Трафик договора по месяцам — `api.report_contract_months(p_contract_id, p_from, p_to)` — с использованием индекса и без использования индекса

- Это **один запрос**. В ПЗ пойдут один снимок результата и два вывода `EXPLAIN ANALYZE` одного и того же вызова с теми же параметрами.
- По месяцам периода: месяц (`sec.period_title`), сеансов, Мб, сумма; строка «Итого» (`ROLLUP`).
- Условие на данные — `se.contract_id = p_contract_id` и период. Таблицы: сеанс ⋈ договор (видимость) ⋈ тариф или тип абонента — что нужно для колонок.
- План «с использованием индекса» — обычный вызов: `Append` по секциям-кварталам периода, в каждой — `Index Scan` или `Bitmap Index Scan` по индексу `(contract_id, started_at)`.
- План «без использования индекса» — тот же вызов в транзакции с `SET LOCAL enable_indexscan = off; SET LOCAL enable_bitmapscan = off;` и `ROLLBACK`: в каждой секции `Seq Scan`. Индекс не удалять. Результат обоих вызовов одинаковый, разные только план, время и число прочитанных страниц (`BUFFERS`).
- Пример: договор оператора «ДонНет» с сеансами в каждом месяце, январь–сентябрь 2026.
- Видимость и отказ для чужого договора — как в запросе 2 (`api.q_contract_sessions`).
- Группы: оператор, руководитель, главный аналитик.

### 21. Абоненты, пользовавшиеся тарифом — `api.q_tariff_subscribers(p_tariff_id, p_from, p_to, p_provider_id DEFAULT NULL, p_limit, p_offset)` — подзапрос с IN

- Абоненты, у которых за период были сеансы по тарифу: наименование, тип, город, число договоров у видимых провайдеров. Условие:
  `s.id IN (SELECT c.subscriber_id FROM core.session se JOIN core.contract c ON c.id = se.contract_id AND c.provider_id = se.provider_id WHERE se.tariff_id = p_tariff_id AND <период> AND se.provider_id = ANY (v_scope))`.
- Почему `IN`, а не соединение: соединение с сеансами повторило бы абонента столько раз, сколько у него сеансов. Здесь нужен только факт.
- Пример: тариф «Образовательный». Генератор (seed 020) назначает его только школам, колледжам и вузам — это одна из проверок группы 14.
- Группы: руководитель, главный аналитик.

### 23. Абоненты с трафиком выше среднего — `api.q_subscribers_above_avg(p_from, p_to, p_provider_id DEFAULT NULL, p_limit, p_offset)` — подзапрос с операциями над итоговыми данными

- Из макета ЛР 4 («Трафик выше среднего по провайдеру»). Там же образец результата: наименование, тип, трафик, % выше среднего.
- Внутренний запрос — трафик каждого абонента за период (`sum` по абоненту). Скалярный подзапрос — среднее этих итогов (`avg` над `sum`). Внешний запрос — абоненты, у которых итог больше среднего. Колонки: наименование, тип, Мб, среднее, «выше среднего, %» = (Мб / среднее − 1) × 100; `total_count`.
- Нужен именно подзапрос, не оконная функция: окно над итогами уже есть в запросе 22.
- Группы: руководитель, главный аналитик.

## 4. Тесты — `db/tests/090_queries_coursework.sql`, группа 14 (подключить в `run_all.sql`)

Каждый новый запрос сверить с независимым расчётом от суперпользователя. Кроме того:

- 17: сумма по типам = строка «в том числе …» = «Всего»; действующих не больше, чем всего; у руководителя «Всего» договоров = договоры его провайдера.
- 18: маска `*школа*` = независимый `LIKE '%школа%'`; ввод `%` ищет символ `%`, а не всё подряд; пустая маска — ошибка.
- 19: «Итого» = итоги запроса 2 по тому же договору и периоду; при `SET LOCAL enable_indexscan = off, enable_bitmapscan = off` результат тот же; чужой договор — как в запросе 2.
- 21: абоненты не повторяются; у «Образовательного» — только школы, колледжи, вузы.
- 23: все строки выше среднего, и ни один такой абонент не пропущен; процент сходится.
- Права: каждый из запросов 17–23 вызвать от имени каждой роли — разрешённые получают результат, остальные отказ (по образцу 12.17).
