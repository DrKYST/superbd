## 1. Триггеры (ТЗ п. 3; план — `requirements.md`, раздел 5; D2, D3, D8, D9, D10, D13, D14)

Нужно не меньше шести триггеров, по одному на каждый тип события (BEFORE/AFTER × INSERT/UPDATE/DELETE), минимум на двух таблицах. Уже есть два:
- `trg_app_user_biu_check_role` — BEFORE INSERT/UPDATE на `sec.app_user`;
- `trg_provider_ai_contract_partition` — AFTER INSERT на `core.provider`.

Их можно засчитать, но план раздела 5 — главный:

| Событие | Таблица | Что делает |
|---|---|---|
| BEFORE INSERT | `core.session` | дата сеанса — в периоде действия договора; тариф по окну времени и типу дня, если не задан (D2, D13); снимок скидки и расчёт стоимости (D3) |
| BEFORE UPDATE | `core.contract` | стороны договора не меняются (D14); `row_version + 1`, проверка конфликта версии (D8) |
| AFTER INSERT / UPDATE / DELETE | `core.contract` | запись в `audit.change_log`: new, old/new, old в jsonb (D10) |
| BEFORE DELETE | `core.provider` | запрет, если у провайдера есть сеансы за последние 12 месяцев (D9) |

Учесть:
- `core.session` и `core.contract` секционированы (D30). Триггеры объявлять на родителе. Проверить, что секции, которые потом создают `sec.session_partitions_ensure` и `sec.contract_partition_ensure`, получают триггеры автоматически (тест).
- Генератор (`db/seed/020_generate.sql`) сам считает скидку и стоимость 500 000 сеансов. Триггер не должен заметно замедлить сборку: замерить время `build.sql` до и после. Если стало намного дольше — предложить студенту вариант, сам не выбирать.
- Журнал (`audit.change_log`) после этого перестанет быть пустым. Экран «Журнал изменений» администратора БД и снимок `dba_change_log.png` должны показывать записи.

Тесты — новая группа, в том числе план `requirements.md`, раздел 10: T7 — удаление провайдера с недавними сеансами отвергается; T8 — сеанс раньше даты подключения отвергается, тариф подобран, стоимость рассчитана. Кроме того: неизменность сторон договора, версия строки, записи журнала для всех трёх событий.

## 2. Модифицируемое представление (ТЗ п. 6; план — `requirements.md`, раздел 5)

Нужно `api.v_contract_card` — «абонент + договор» — с триггерами INSTEAD OF INSERT / UPDATE / DELETE:
- права проверяются внутри (группа, свой провайдер);
- общий реестр абонентов (D25): найденный абонент присоединяется, а не копируется; сведения общего абонента меняет только администратор приложения;
- оптимистическая блокировка по `row_version`.

Это представление использует форма «Договор» в клиенте (этап 5). Тесты — новая группа: вставка, изменение и удаление через представление, отказ чужому провайдеру и другим ролям.

## 3. Защита на уровне строк (ТЗ п. 8; план — `requirements.md`, раздел 3; D25, D30)

- `ENABLE` + `FORCE ROW LEVEL SECURITY` на `core.provider`, `core.subscriber`, `core.contract`, `core.session`. На секциях — `ENABLE` + `FORCE` без политик, прямое обращение к секции запрещено (D30).
- Политики — через `session_user` (функции `sec.*`), по таблицам из раздела 3: оператор и руководитель видят договоры и сеансы своего провайдера; абонентов — тех, у кого есть договор с их провайдером; главный аналитик — всё; администратор приложения — реестр абонентов без договоров и сеансов.
- Условия видимости в функциях `api` оставить: RLS — второй рубеж.
- Проверить, что все 140 прежних тестов проходят. Замерить время ключевых запросов (журнал сеансов, абоненты, отчёты 15 и 22) до и после: страница списка должна укладываться в 1 с.

Тесты — новая группа: прямое чтение с `SET SESSION AUTHORIZATION` каждой ролью, отказ чтению секции напрямую, одинаковый результат функций `api` до и после включения RLS.

## 4. Серверные функции для форм ввода

Сейчас есть `contract_create`, `contract_update`, `subscriber_update`, `subscriber_delete`, `user_create`, `user_set_login`, `user_reset_password`. Не хватает (по `requirements.md`, разделы 4 и 8):

- расторжение договора;
- провайдер: создание, изменение, удаление (администратор приложения);
- справочники: типы собственности, города, типы абонентов, тарифы (администратор приложения);

Оформление — как у существующих функций (`.claude/rules/sql.md`): `SECURITY DEFINER`, проверка группы первой строкой, понятные сообщения об ошибках, `row_version` там, где есть. Тесты — на каждую функцию, в том числе отказ другим ролям.
