## D1. IP-адрес хранится в договоре, а не у абонента
Обоснование: IP назначает провайдер в рамках договора; абонент с договорами у двух провайдеров имеет два IP. Хранение у абонента требует многозначного атрибута (нарушение 1НФ) или теряет данные. Тип `inet`, частичный уникальный индекс `(provider_id, ip_address) WHERE closed_on IS NULL`.
Статус: принято студентом (2026-09-29); обосновать на защите ЛР 2 (в задании IP перечислен у абонента).

## D2. Тариф сеанса подбирается триггером по времени
`ref.tariff` хранит окно `time_from..time_to` и признак выходного дня. BEFORE INSERT на `core.session` подбирает тариф, если он не указан явно. Окно через полночь (ночной 23:00–09:00) обрабатывается условием `time_from > time_to`.
Статус: предложено.

## D3. Снимок скидки и стоимости в сеансе (осознанная денормализация)
`core.session.discount_pct` и `cost` вычисляются триггером при вставке и больше не меняются. Обоснование: изменение справочника тарифов или цены договора не должно менять уже выставленные суммы; отчёты по 50–500 тыс. сеансов не пересчитывают формулу с тремя соединениями. ТЗ п. 1 требует обосновать денормализацию — это обоснование идёт в 4.1 ПЗ.
Статус: предложено.

## D4. Справочник городов
Город провайдера и абонента — FK на `ref.city`; улица/дом — текстом в `address`. Нужен для фильтров статистики и UNION-запроса контактов.
Статус: предложено.

## D5. Разграничение по провайдерам
Оператор и руководитель привязаны к провайдеру через `sec.app_user.provider_id`. RLS по `provider_id` на `core.contract`, `core.session` (через договор) и `core.subscriber` (через наличие договора или `created_by`). Главный аналитик (`grp_chief`) видит всё.
Уточнено D17 (2026-09-30): абонент принадлежал провайдеру, колонка `created_by` удалена. Уточнено D25 (2026-10-05): абонент — общий реестр; оператору и руководителю виден абонент, у провайдера которых есть с ним договор; главному аналитику и администратору — весь реестр (администратору — без договоров и сеансов).
Статус: предложено.

## D6. Доступ только через функции SECURITY DEFINER + FORCE RLS + session_user
Группы не получают прав на таблицы. Функции `api.*` принадлежат `app_owner`, выполняются от его имени; на таблицах `FORCE ROW LEVEL SECURITY`, политики используют `session_user`. `ALTER DEFAULT PRIVILEGES … REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`, иначе любая новая функция доступна всем.
Альтернатива (SECURITY INVOKER + права на таблицы) отвергнута: пользователь смог бы обойти функции прямыми запросами.
Статус: предложено.

## D7. Роль «гость» — опционально
Если преподаватель потребует: LOGIN-роль `guest` в группе `grp_guest`, доступ только к `api.catalog_*`. Пароль гостя не зашивается в код: берётся из `client/config.ini` или разрешается `trust` для `guest` в `pg_hba.conf` на localhost.
Статус: отменено (2026-09-29) — роль «гость» не делается, группы: `grp_admin`, `grp_operator`, `grp_manager`, `grp_chief`.

## D8. Оптимистическая блокировка договоров

Статус: предложено.

## D17. Абонент принадлежит одному провайдеру (у каждого провайдера свои абоненты)
Как в биллинговых системах операторов (UTM5, LANBilling, Hydra, BGBilling): каждый провайдер ведёт своих абонентов, один и тот же человек у двух провайдеров — две независимые записи. Выбрано студентом вместо общего реестра абонентов с провайдером-владельцем (вариант 1С/SAP Business Partner).
- `core.subscriber.provider_id` NOT NULL, FK на `core.provider` ON DELETE RESTRICT (связь R5 «Провайдер — Абонент» вместо прежней «Провайдер — Договор»).
- Договор сохраняет `provider_id` (в задании договор заключается с провайдером), но ссылается на абонента составным ключом `(subscriber_id, provider_id) → core.subscriber (id, provider_id)` ON DELETE CASCADE (R6): договор с абонентом чужого провайдера невозможен. Формально `provider_id` договора транзитивно зависит от абонента — осознанное повторение, согласованность гарантирует внешний ключ; нужно для уникальности номера договора и IP в пределах провайдера и для RLS без соединения с абонентом.
- `core.subscriber.created_by` удалена: видимость абонентов без договоров теперь даёт `provider_id` (D5).
- Каскадное удаление абонента (D9) безопасно: все его договоры принадлежат тому же провайдеру. Перенос абонента к другому провайдеру — новая запись у нового провайдера.
- Следствия: RLS проще (у всех таблиц `core` провайдер в строке или через договор); сводка главного аналитика считает записи абонентов, а не уникальных людей (сопоставление людей между провайдерами не делается — его нет и в реальных биллингах); D1 (IP в договоре) остаётся в силе: у абонента может быть несколько договоров (точек подключения) у своего провайдера.
Статус: заменено D25 (2026-10-05): записи-копии абонента у каждого провайдера на практике оказались неудачными.

## D19. Часовой пояс предметной области фиксируется в функциях БД
Драйвер Qt QPSQL сразу после подключения выполняет `SET TIME ZONE 'UTC'`, psql и pgAdmin работают в часовом поясе сервера (`Europe/Moscow`). Бизнес-правила зависят от местного времени: тариф сеанса по времени суток и дню недели (D2/D13), «сегодня», границы месяца в отчётах. Чтобы результат не зависел от клиента, все функции `api.*` и триггерные функции объявляются с `SET TimeZone = 'Europe/Moscow'` (наряду с `search_path`); данные хранятся в `timestamptz`, поэтому момент времени не меняется. Клиент показывает время в местном поясе компьютера (`toLocalTime()`).
Проверка: тест 6.7 — результат `api.home_todo()` одинаков при сеансе в UTC и в Europe/Moscow.
Статус: принято (обнаружено при разработке клиента, 2026-09-30).

## D24. Без регулярных выражений; запросы и бизнес-логика — в оптимизированной форме
Регулярные выражения не используются ни в БД (домены, ограничения, функции, представления), ни в клиенте: допустимые символы проверяются `translate()` (удаляет разрешённые символы — должна остаться пустая строка), поиск — `LIKE` по шаблону-префиксу, цифры телефона — `translate()`. Разбор шаблона регулярного выражения дороже и нечитабелен для проверяющего; проверка тестом 8.1 (поиск `regexp_`, `~`, `SIMILAR TO` в определениях объектов).
Правила оптимизации запросов (Карпова Т. С., гл. 9 — синтаксическая оптимизация; Лузанов П. В. и др., «Postgres. Первое знакомство» — индексы):
- условия в канонической форме «столбец ОС константа»: видимость строк — одно условие `provider_id = ANY (массив)`, массив считают `sec.scope_data()` / `sec.scope_providers()` один раз до запроса (в представлениях — `(SELECT …)::integer[]`, InitPlan); прежняя дизъюнкция `(видит_всех OR provider_id = свой)` индекс не использовала — таблицы читались целиком;
- выражения от ввода пользователя (шаблоны поиска, цифры телефона, верхний регистр номера договора) вычисляются один раз в `DECLARE`, а не для каждой строки; условие, которое не нужно (поиск по IP без цифр), превращается в `NULL` и сворачивается планировщиком;
- необязательные отборы `(p IS NULL OR столбец = p)` — в функциях с `SET plan_cache_mode = force_custom_plan`: план строится с фактическими значениями, и лишние условия исчезают;
- выборка до соединения: условие на провайдера ставится на договор, абоненты отбираются полусоединением `EXISTS` договора с видимым провайдером по индексу `(subscriber_id, provider_id)` (D25; до D25 условие ставилось и на абонента — D17); группировка до соединения (запрос 9) и по первичным ключам (запрос 8);
- индексы под условия экранов: `(provider_id, connected_on)` вместо `(connected_on)` — для всех провайдеров сразу PostgreSQL 18 использует пропуск по первой колонке (Skip Scan).
Результат на тестовых данных (оператор «ДонНет», `labs/lab05/explain/`): представления абонентов и договоров читают 275 и 399 строк по индексу вместо 8 000 и 12 002; запрос 8 — 399 договоров вместо 12 002; запрос 4 — 1,75 → 0,95 мс. После D25 (2026-10-05): договоры провайдера — по индексу провайдера (409 строк), абоненты — полусоединением с ними (289 абонентов, `Hash Semi Join`); видимость абонентов записана ветвями `UNION ALL` с условием-константой, а не `видит_всех OR EXISTS (…)`, — иначе подзапрос проверялся бы для каждой из 8 000 строк.
Уточняет D22 (видимость строк до RLS).
Статус: принято (замечание студента, 2026-10-01).

## D25. Общий реестр абонентов; данные, различающиеся у провайдеров, — в договоре (вместо D17)
Абонент — одна запись на человека или организацию, сколько бы провайдеров его ни обслуживали (как Business Partner в SAP: общие данные отдельно, данные по организации отдельно). Договор — таблица пересечения провайдера и абонента (связь M:N).
- `core.subscriber`: без провайдера; наименование, тип, город, физический адрес, основной телефон, `row_version`. Дубли отсекает уникальный индекс `(lower(name), цифры телефона)`.
- `core.contract`: FK на провайдера (RESTRICT) и на абонента (CASCADE) отдельно; новые поля «Адрес подключения» (обязательно), «Контактный телефон», «Контактное лицо».
- Видимость (`api.v_subscribers`, `api.q_subscribers`): оператор и руководитель видят абонента, пока у их провайдера есть с ним договор; главный аналитик и администратор — весь реестр. Договоры (`api.v_contracts`, `api.q_contracts`) — только своего провайдера, администратору недоступны.
- Абонент появляется вместе с первым договором (`api.contract_create`): если в реестре есть абонент с тем же наименованием и телефоном, договор заключается с ним, а не с дублем. Чужого абонента по коду не выбрать (только по точному наименованию и телефону, `api.subscriber_find_exact`).
- Сведения реестра (`api.subscriber_update`): оператор меняет своего абонента, пока его не обслуживают другие провайдеры; общего абонента меняет администратор (решение студента, 2026-10-05). Удалить общего абонента нельзя никому (каскадом ушли бы чужие договоры). Адрес подключения и контакты меняются в договоре (`api.contract_update`). Оптимистическая блокировка по `row_version`.
- Тестовые данные: у ~8 % абонентов договоры с несколькими провайдерами. Тесты — `db/tests/040_shared_subscribers.sql`.
- Попутно: генератор и тесты работают в часовом поясе Europe/Moscow (D19), иначе ночью по Москве тест 7.3 падал.
Обновлены 2026-10-05: концептуальная модель и диаграмма таблиц ЛР 2 (связь «Провайдер — Договор», новые поля договора и абонента), `labs/lab02/model.md`, `domain.md`, `requirements.md` §3–4, `queries-plan.md` (запрос 21 снова возможен), D5, D24, README ЛР 2, 3, 5, подразделы 1 и 4 ПЗ, `labs/lab05/explain/`.

## D26. Два администратора: администратор приложения и администратор БД
Роль «администратор» разделена на две группы PostgreSQL.
- `grp_admin` — администратор приложения: учётные записи операторов, руководителей и главных аналитиков (создание, запрет входа), справочники, провайдеры, сведения общих абонентов (D25). Журнала изменений и состояния базы не видит.
- `grp_dba` — администратор БД: учётные записи администраторов приложения; журнал изменений (`api.q_change_log`), таблицы (`api.db_tables`), подключения (`api.db_connections`). Абонентов, договоры, сеансы, справочники через `api` не видит. Встроенные роли: `pg_monitor` (состояние сервера, запросы других сеансов), `pg_maintain` (VACUUM, ANALYZE, REINDEX; PostgreSQL 17+), `pg_read_all_data` (чтение всех таблиц для `pg_dump`). Структуру меняет от имени владельца: членство в `app_owner` с `INHERIT FALSE, SET TRUE` — права владельца не действуют, пока не выполнен `SET ROLE app_owner`.
- Кто кого создаёт: первого администратора БД — `postgres`; администраторов приложения — администратор БД; остальных — администратор приложения (`api.user_create`, `api.user_set_login`; список — `api.q_users`). Функции выполняют `CREATE ROLE`, `GRANT`, `ALTER ROLE` от имени `app_owner`, у которого право ADMIN на группы (`WITH ADMIN TRUE, INHERIT FALSE, SET FALSE`, миграция 010) и на созданные им роли (PostgreSQL 16+). Учётными записями администраторов БД приложение не управляет: выдать `app_owner` право ADMIN на них нельзя — администратор БД сам входит в `app_owner`, членство стало бы циклическим.
- Группа пользователя — по прямому членству с наследованием (`sec.group_of`). `pg_has_role(…, 'MEMBER')` учитывает и косвенное членство: через `app_owner` администратор БД формально «состоял» бы во всех группах.
- Исключение из правила «у групп нет прав на таблицы»: `pg_read_all_data` у администратора БД — только чтение, для резервного копирования; через приложение данных он не видит. Если преподаватель не примет — резервные копии делает `postgres`, а строка `GRANT pg_read_all_data` убирается из миграции 010.
- Начальная страница: у администратора приложения счётчик «Изменений в журнале за сегодня» заменён на «Пользователей системы» (журнал — у администратора БД); у администратора БД — размер данных, подключения, изменения за сегодня, таблицы без свежей статистики.
- Клиент: разделы администратора БД «Администрирование» (Пользователи, Журнал изменений) и «База данных» (Таблицы, Подключения); экранов в макете нет — пока заглушки, отличия — `docs/ui/deviations.md`.
- Тесты — `db/tests/050_admin_split.sql` (10.1–10.15); всего 87 из 87 на PostgreSQL 16 и 18.
Статус: принято (решение студента, 2026-10-07).

## D27. Сброс пароля: временный пароль и смена при первом входе
Администратор (по правилам D26) сбрасывает пароль сотрудника: сервер генерирует временный пароль (12 символов, `gen_random_uuid()`), ставит его с `VALID UNTIL now() + 1 день`, отмечает в `sec.app_user` «нужно сменить пароль» и возвращает пароль один раз. Пока флаг стоит, `sec.require_group` и функции области видимости отказывают во всём, кроме `api.whoami` и `api.change_own_password`; клиент после входа открывает форму «Смена пароля». `api.user_create` сразу выдаёт временный пароль. Временный пароль не хранится в таблицах проекта и не попадает в журнал изменений. Подробный план, безопасность, тесты — `docs/analysis/password-reset.md`.

## D29. ЛР 7: документ — учётная запись сеанса из биллинга провайдера (jsonb)
Документ ЛР 7 — учётная запись сеанса связи, которую биллинг провайдера выгружает по каждому завершённому сеансу: источник (провайдер; сервер доступа NAS — производитель, модель, расположение), договор (номер, IP), сеанс (Acct-Session-Id, логин, начало и окончание, длительность, причина завершения, трафик по направлениям в Мб и пакетах), тарификация (тариф с окном времени, цена 1 Мб, скидка, стоимость), атрибуты оборудования, журнал событий (start, промежуточные обновления раз в час, stop). В предметной области — вход процесса 3 «Регистрация сеансов» (`docs/analysis/domain.md`: «в реальности — загрузка из биллинга»); строка `core.session` — разобранная часть такой записи.
- Почему jsonb: набор атрибутов зависит от производителя оборудования доступа (MikroTik, Cisco, Juniper, Huawei, Accel-PPP) и меняется с прошивкой: ограничение скорости, пул адресов, порт, признак должника передаются разными ключами. В реляционной модели — колонки под каждого производителя или таблица «ключ — значение»; документ хранится целиком, как пришёл, нужное извлекается запросами.
- Отклонено предложение `lab-notes.md` («провайдер → contracts[] → sessions[]»): это перенос реляционной модели в один документ — дублирование `core.*` без причины из предметной области, документ провайдера растёт без предела (TOAST, перезапись целиком при каждом новом сеансе).
- Данные — из базы курсовой: каждый сеанс `core.session` → запись (договор, провайдер, тариф, объём, скидка, стоимость — из `core`/`ref`, остальное достраивается), плюс `generate_series`: служебные сеансы наладки NAS (без договора) и неудачные подключения (без трафика) — их удаляет ЛР; `setseed`, результат повторяем.
- Связь с курсовой: запрос 5.4 разбирает запись в строку `core.session` (`jsonb_populate_record` в тип строки таблицы), 5.5 сверяет выгрузку с учётом (100 025 из 100 025 совпали). Загрузка выгрузок в курсовую не переносится — в ТЗ её нет. Журнал `audit.change_log` (D10, тоже jsonb) в ЛР 7 не делается: его заполняют триггеры курсовой — отдельная работа.
- Оформление: схема `lab7` (D11), скрипты `labs/lab07/sql/NN_*.sql`, `db/migrations` и `core.*` не меняются; ключи — английские `snake_case`; время — ISO 8601 с точностью до секунды и смещением +03:00 (D19); без `like_regex` (D24). Индексы: GIN `jsonb_path_ops` по документу целиком (образец и jsonpath; меньше `jsonb_ops`: 75 против 85 МБ), GIN `jsonb_ops` по `attributes` (наличие ключа `?|`), уникальный B-дерево «провайдер + Acct-Session-Id» (повторная выгрузка сеанса отвергается), B-дерево по времени начала — строка ISO 8601 с `COLLATE "C"` (приведение к `timestamptz` не `IMMUTABLE`). Структура — `labs/lab07/structure.md`, материалы — `labs/lab07/`.
Статус: принято (предложение Claude, принятое студентом в постановке ЛР 7; выполнено 2026-10-12).

## D30. Секционирование `core.session` — настоящее, при создании базы (ЛР 8)
Предупреждение преподавателя: секции «для галочки» не принимаются, базу, скорее всего, придётся пересоздать. Прежний план — схема `lab8` с копиями таблицы сеансов, затем «перенести лучшее» в курсовую (`lab-notes.md`, `requirements.md` §7) — пересмотрен: секционируется рабочая таблица.
- `core.session` создаётся в миграции 040 как `PARTITION BY RANGE (started_at)` в два уровня: **год → квартал** (вложенные секции варианта 16), секция `DEFAULT` на верхнем уровне. Годы 2024 … текущий + 1 создаёт функция `sec.session_partitions_ensure` (новая миграция 042): таблица года с четырьмя кварталами, `ATTACH PARTITION`, перенос строк из `DEFAULT`, если они там оказались; запас — год. Администратор БД вызывает `api.db_session_partitions_ensure()` раз в год (D26); расширения (`pg_partman`, `pg_cron`) не используются.
- Почему так: сеансы — единственная неограниченно растущая таблица со сроком хранения; старый год отсоединяется целиком (`DETACH`), очистка, сбор статистики и перестроение индексов — по кварталу, отчёты за период читают только свои секции. На объёмах курсовой (100–500 тыс. строк, 7–35 МБ) выигрыш по времени мал, а запросы по договору без даты дороже (спуск по индексу в каждой секции) — показывать честно. Месяц (48 мелких секций) и год (секция 2026 — половина таблицы) отвергнуты; квартал → список тарифов (прежний план) отвергнут: тариф не отбирается экранами и не обслуживается отдельно.
- Следствия: первичный ключ `(id, started_at)` уже есть (040); вставка только через родителя (в PostgreSQL 16 секции не наследуют identity); таблицы годов — `LIKE … INCLUDING DEFAULTS INCLUDING CONSTRAINTS`, без identity; RLS (этап курсовой) — на родителе, на секциях `ENABLE` + `FORCE` без политик (прямое обращение — запрет по умолчанию); `api.db_tables` сворачивает секции в строку `core.session` (макет «Таблицы базы данных» не меняется), счётчик статистики администратора БД — по логическим таблицам; тесты 1.1, 1.4, 1.5 — без секций (`NOT relispartition`), новые 13.x; изменение `started_at` сеанса не допускается (снимок D3).
- Партиция № 2 (по списку) и обычная таблица — копии в схеме `lab8` только для сравнения (задание: «скопировать данные из партиции № 1»). Осмысленный ключ списка — провайдер, его нет в `core.session` (через договор): в копию код провайдера берётся из договора. Вопрос преподавателю; альтернатива — провайдер в `core.session` (денормализация, отдельное решение).
- Объём ≥ 500 000 — в рабочей таблице: число сеансов — параметр генератора (по умолчанию 500 000), сеансы распределяются пропорционально договоро-месяцам (сейчас ~8,4 сеанса на договор при любом сроке действия — последние месяцы перегружены). Вопрос преподавателю; ЛР 7 остаётся на 100 000 записей.
Анализ по данным, влияние на функции `api.*`, тесты, экраны, пошаговый план — `docs/analysis/partitioning.md`. Заменяет план секционирования `requirements.md` §7 и `lab-notes.md` (ЛР 8).
