## Архитектура — жёсткие правила (из методички, нарушение = снижение оценки)

1. **Толстая БД, тонкий клиент.** Бизнес-логика, проверки, расчёты, авторизация, роли — в PostgreSQL. Клиент на Qt только вызывает функции `api.*` и показывает результат.
2. **Роли — только средствами PostgreSQL.** Пользователь = LOGIN-роль, член группы `grp_admin` / `grp_dba` / `grp_operator` / `grp_manager` / `grp_chief` (роли «гость» нет — D7 отменено; администратор приложения и администратор БД — D26). Запрещено: пароли в коде, таблица «users» с ролями или паролями, проверка роли по полю таблицы.
3. **Все обращения к данным — через функции/представления схемы `api`.** Группы не имеют прав на таблицы `core`/`ref` (исключение — чтение всех таблиц администратором БД для резервных копий, D26). Функции `SECURITY DEFINER`, `SET search_path = pg_catalog, pg_temp`, первая строка — проверка группы.
4. **RLS** на `core.*` с `ENABLE` + `FORCE ROW LEVEL SECURITY`, в политиках — `session_user` (не `current_user`).
5. **Пагинация** в каждой функции-списке: `p_limit`, `p_offset`, колонка `total_count`.
6. **ID не показывать пользователю**, если роли они не нужны. На клиенте ID живут в `Qt::UserRole` / скрытых колонках.
7. **Одна страница на тему**, инструменты показываются по роли. Отдельные страницы на одну тему для разных ролей запрещены.
8. Запросы без параметров → представления `api.v_*`; с параметрами → функции `api.q_*` / `api.report_*`.
9. **Источник требований — только `docs/task/*` и `docs/decisions.md`.** Прошлые работы студента (курсовая на другую тему) — только образец оформления, их содержание в проект не переносить. Оформление ПЗ — чистый шаблон `tools/md2docx/templates/pz-template.docx` (без текста); сам образец лежит вне репозитория.

Подробности и обоснования: `docs/analysis/requirements.md`, решения — `docs/decisions.md` (новое решение = новая запись Dxx).

## Команды

```bash
# БД (локальный PostgreSQL 16+, пароль — в ~/.pgpass или PGPASSWORD, не в файлах репозитория)
psql -U postgres -d postgres -v ON_ERROR_STOP=1 -f db/create_db.sql # один раз: база superbd и роль app_owner
psql -U postgres -d superbd -v ON_ERROR_STOP=1 -f db/build.sql     # пересобрать всё (схемы + данные)
psql -U postgres -d superbd -v ON_ERROR_STOP=1 -f db/tests/run_all.sql

# Клиент
cmake -S client -B client/build -DCMAKE_PREFIX_PATH=<путь к Qt6>
cmake --build client/build

# Отчёт по лабе / ПЗ
python tools/md2docx/md2docx.py labs/lab02/report.md -o labs/lab02/out/lab02.docx --kind lab --lab 2
python tools/md2docx/md2docx.py coursework/pz/_pz.md -o coursework/out/pz.docx --kind pz
```

Зависимости Python: `pip install python-docx pyyaml`.

## Проверка работы

- Любой SQL — прогнать на локальной БД с `ON_ERROR_STOP=1` перед тем, как говорить «готово». Если БД недоступна — прямо сказать, что скрипт не проверен.
- После изменений прав/RLS — прогнать `db/tests/` (тесты используют `SET SESSION AUTHORIZATION`).
- Готовый .docx — открыть/сконвертировать и проверить, что заглушки скриншотов на месте и нумерация рисунков/таблиц сквозная.
- Скриншоты делает студент. В отчёте ссылаться на файл `screenshots/<имя>.png`; если файла нет, генератор вставит видимую заглушку «ВСТАВИТЬ СКРИНШОТ».
